# LLM 응대 튜닝 (AG-T10a)

- 측정: 2026-11-19 · LLM `gemini-3.5-flash-lite`(폴백 `gemini-3.1-flash-lite`, 첫 이벤트 2.5초) · 심사 `gemini-3.8-flash`(eval.score 심사 함수)
- 도구: `eval/llm_eval.py`(오프라인 LLM 평가기). 오디오 없이 `data/testset/cases.jsonl` 172문항의 정답 텍스트·history·caller·now로 **실제 프롬프트(agent/prompts.py) + 실제 Responder 툴 루프**를 돌린다. 툴은 `mock_api` `load_shop().lookup` 직접 호출, 인자 정규화는 `agent.normalize.normalize_args`. 함수 일치는 `eval.score.tool_match`(이름 + 키 인자, 자유 텍스트 제외, 기대 []인데 호출하면 0).
- 명령: `uv run python -m eval.llm_eval [--judge] [--category ...] [--concurrency 4]`, 비교 `uv run python -m eval.llm_eval --compare runs/A runs/B`
- 원시 결과: `runs/llm_eval_base1`(베이스라인, 심사), `runs/llm_eval_base2`(베이스라인), `runs/llm_eval_impr1`(개선, 심사), `runs/llm_eval_impr2`, `runs/llm_eval_impr3`, `runs/llm_eval_impr4`(최종 코드: 자릿수 되묻기 규칙 포함), 반복 실험 `runs/llm_eval_iter1~4`(약점 4범주 100문항)
- 주의: STT 오류가 없는 정답 텍스트로 잰 값이다. E2E 점수는 STT·턴 감지 영향을 더 받는다.

## 바꾼 것

### 프롬프트 (agent/prompts.py)
고정부(앞, 캐시 대상)를 세 절로 다시 썼다. 테스트셋 문장은 넣지 않았다(`tests/test_prompts.py`가 확인).
- **말하는 방식**: 응답은 첫 마디("네, 고객님.") 바로 뒤에 이어지는 말이다. 첫머리에 호칭("고객님", "○○○ 고객님")·인사("안녕하세요", "다이렉트몰 고객센터입니다")·맞장구("네")를 다시 넣지 않는다. 2~3문장, 첫 문장은 짧게 결론부터. 번호 되읽기는 `digits_for_speech` 형식("이육일일, 일오공, 이삼일" / "공일공, 일이삼사, 오육칠팔")으로, 매뉴얼 예시보다 우선한다. 긴 송장번호는 읽지 않는다.
- **함수 사용 규칙**
  - 함수가 필요하면 먼저 함수만 호출하고 말은 결과를 받은 뒤에 한다. 호출하지 않았으면 "접수됐어요"·"연결해 드릴게요"처럼 처리된 것처럼 말하지 않는다.
  - 정책 질문(FAQ)·범위 밖 질문은 함수 없이 답한다.
  - 인계 조건(매뉴얼 9절 목록)에 해당하면 말로만 하지 말고 **반드시 `transfer_to_agent`**. 상담원 연결은 말이 아니라 함수 호출로만 이루어진다. 번호를 묻거나 조회하지 않는다.
  - 상담원 연결 시간이 아니면 `transfer_to_agent` 대신 `request_callback`.
  - 실행 요청(취소·반품·교환·주소 변경) + 주문번호가 있으면 실행 함수를 바로 호출한다. 상태 확인용 `get_order_info`를 먼저 부르지 않고, "배송중이라 안 될 것" 같아도 호출을 건너뛰지 않는다(결과의 not_allowed로 안내).
  - caller 전화번호가 있으면 다시 묻지 않는다. 주문번호 없이 주문 이야기를 하면 `get_order_list` → 상품명·날짜로 하나로 정해지면 이어서 실행, 정해지지 않으면 어느 주문인지 묻는다. 고객이 주문번호를 말했으면 `get_order_list`를 거치지 않는다.
  - caller가 없고 번호도 안 말했으면 되묻기만 한다(실행 요청이어도).
  - history에 이미 조회·안내한 정보는 다시 조회하지 않는다. 직전 상담원이 처리를 위해 번호를 물었고 고객이 번호를 답하면 조회 함수 말고 그 처리 함수를 부른다. "~해 드릴까요?"에 동의하면 실행한다.
  - 함수 선택: 배송은 `track_delivery`, 상태·금액은 `get_order_info`, 재고·옵션 유무는 `check_stock`, 가격·사양은 `get_product_info`. 상품을 종류 이름으로만 말해 상품명이 분명하지 않으면 먼저 확인한다.
  - 번호 인자: 한글로 읽은 번호는 직접 숫자로 바꾸지 말고 들은 그대로 넣는다(`normalize_args`가 바꾼다). 다만 LLM은 이 지시를 잘 따르지 않아 응답기에서 따로 교정한다(아래).
- **함수 결과 안내**: ok / not_allowed / not_found / no_refund / invalid_arguments별 매뉴얼 문구(배송준비 취소는 "취소 요청 접수, 1영업일 안에 확정 문자").
- **세션 가변부**: 현재 시각에 요일을 붙이고, now 기준 **상담원 연결 가능 여부**(`business_hours_note`: 평일 09~18시, 점심 12~13시 제외, 주말 휴무)를 한 줄로 넣는다. caller 전화번호가 있으면 전화번호를 받는 함수 목록과 함께 "그 번호를 바로 넣는다". history가 있으면 원문 뒤에 **요약**(`history_summary`)을 붙인다: 이전 대화에 나온 번호(한글로 읽은 번호는 숫자로 바꿔서), 직전 상담원 질문("이번 고객 말은 이 질문에 대한 답이다"), 재조회 금지.
- 툴 설명(`mock_api/data/tools.json`)은 고치지 않았다.

## 첫 마디와 본 응답 사이 공백: 원인과 session 쪽 제안

턴 로그(`runs/logs/turns-20261119.jsonl` 최근 20턴)로 본 선호출 흐름:
- 선호출은 20턴 중 17턴에서 **시작은 된다**(침묵 200 ms에 `latest_text()`가 있음). 재사용은 2턴뿐이다.
- 버려진 15턴은 모두 **부분 결과가 마지막 1~3어절을 놓친 상태**였다. 예: "영업 시간이" vs 최종 "영업 시간이 어떻게 돼요?", "무선 이어폰 에어" vs "무선 이어폰 에어핏 얼마예요?". 띄어쓰기·숫자 표기 차이도 있다("2 6 1 1 1 9 0 2 3 3 …" vs "2611190233 …"). `session._respond_turn`이 `self._prefetch_text.strip() != user_text`로 정확히 비교해서 하나라도 다르면 버린다. 부분 결과 없이 시작조차 못 한 턴은 3턴(짧은 발화)이었다.
- `finalize_done`은 확정(commit)보다 7~440 ms 늦게 끝난다(중앙값 약 150 ms). LLM은 finalize가 끝난 뒤 새로 불리고, 그로부터 첫 이벤트까지 0.6~1.0초가 걸린다. 여기에 TTS 첫 바이트 약 0.66초가 더해져, 약 1초 길이의 첫 마디 뒤에 약 0.9초 공백이 생긴다. 툴 턴은 LLM을 한 번 더 불러 공백이 1.5초를 넘었다.

이번 Task에서 한 것(responder 쪽): 툴 턴에는 필러가 툴 호출 150 ms 뒤에 나간다. 오프라인 측정에서 툴 턴의 "첫 마디 뒤 첫 소리"는 LLM 시작 기준 약 1.2초(필러)다. 필러가 없을 때 본문 첫 문장은 1.6~2.0초였다. 실제 통화로 보면 첫 마디(약 1초 재생) 직후 필러가 이어지고, 필러(약 1.6초)가 끝날 무렵 본문 TTS가 준비된다. 1회차에 바로 답하는 턴(FAQ 등)은 여전히 "LLM 첫 이벤트 + TTS 첫 바이트 − 첫 마디 길이"만큼(약 0.5~0.9초) 빈다.

session/turn 담당 Task에 제안(이번 Task에서는 수정하지 않음):
1. **finalize 완료 즉시 재선호출**: `_finalize_task`가 끝났는데 결과가 선호출 텍스트와 다르면, 확정을 기다리지 말고 그 자리에서 선호출을 다시 건다(done callback). finalize가 확정보다 먼저 끝나는 턴에서 그만큼 앞당겨진다.
2. **비교 정규화**: 재사용 판단을 공백·문장부호를 지운 문자열로, 숫자는 `normalize`로 이어 붙인 형태로 비교한다. 띄어쓰기·마침표 차이로 버리는 일이 없어진다.
3. **부분 결과 안정성 조건**: `latest_text()`가 N ms 동안 바뀌지 않았을 때만 선호출한다. 어차피 버려질 호출을 줄인다(비용·429 여유).
4. **상황별 첫 마디**: 확정 시점 텍스트에 번호·"주문/배송/취소"가 보이면 조금 긴 캐시 문구("네, 고객님. 확인해 보겠습니다.")를 고른다. 지금은 `select_opener`가 세션 시작 때 한 번 정하고 텍스트를 모른다. 바꾸면 툴 턴 필러와 겹치지 않게 `fillers` 쪽도 같이 조정해야 한다.
5. 선호출이 재사용되면 responder의 툴 회차 필러도 그대로 동작한다(1회차가 선호출이어도 같은 경로).

## 남은 문제
- **history만으로는 주문번호를 알 수 없는 후속 턴**(followup 6~7문항): 이전 턴 상담원 말에 상품명만 있고 번호가 없다(이전 턴의 툴 결과는 history에 없다). 기대값은 `get_order_list` 없이 바로 실행인데, 모델은 번호를 찾으려고 `get_order_list`를 먼저 부른다 → 문항당 50점. 정보상 이게 최선이다. 데이터셋 기대값을 점검할 후보(운영진 실제 history 형식 확인 필요).
- **옵션 표기 불일치**: "엑스라지"→`XL`, "회색"→`그레이` 같은 옵션 이름이 Mock과 달라 not_found(T0056, T0068). 상품명도 "후드티" vs "기모 후드티"(T0152), "대용량 보조배터리 만 픽셀"(T0066). 결과의 `available_options`를 보고 다시 부르게 하거나 옵션·상품명 정규화가 필요하다. 다만 실제 대회 함수·데이터가 다를 수 있어 Mock 상품 목록을 프롬프트에 넣지는 않았다.
- **check_stock vs get_product_info**: "15인치도 있어요?"에 `get_product_info`를 부르는 경우가 남았다(T0166).
- **배송 문의에 get_order_info**(T0073), 배송 안내를 정책으로 대신하고 `track_delivery`를 생략하는 경우(T0086).
- **caller 있음 + 주문 특정 안 됨**("환불 언제 돼요?", T0141): 기대는 목록 조회 후 확인 질문인데, 해당 주문이 하나뿐이면 모델이 바로 다음 함수까지 부른다.
- **응대 심사 점수는 함수만큼 오르지 않았다(69.5 → 73.0)**. 감점 대부분은 "2~3문장" 제한으로 기대 항목 일부를 빠뜨린 경우다(조건·날짜·부가 안내 누락). tool_lookup은 59.0 → 57.7로 제자리. 문장 수를 조금 늘리거나 "질문에 필요한 날짜·금액·조건은 빠뜨리지 않는다"를 넣는 실험이 다음 후보다. 심사는 1회씩이라 변동 폭을 모른다.
- **흉내 낸 함수 호출**: "…연결해 드릴게요.이사유: …"처럼 함수 호출을 텍스트로 쓰는 경우가 드물게 남는다. 안전망이 인계만 잡고, 콜백·접수 같은 다른 처리는 잡지 못한다.
- **프롬프트 길이**: 고정부가 3.3천 자가 되어 첫 이벤트 p50이 약 +90 ms 늘었다. Gemini 암시적 캐시가 먹으면 줄어들 수 있다(미확인).
- **폭주 생성**: T0037에서 한 번 나왔다. 300자 상한으로 막았지만 원인(무작위성인지, 특정 프롬프트 조합인지)은 모른다.
