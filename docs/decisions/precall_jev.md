# 말하는 중 Jev 선호출 vs 기존 침묵 선호출 (AG-T34)

> 2026-11-21 · 평가 `eval/precall_jev_eval.py` · 테스트 `tests/test_precall_jev.py` · 데이터 onedam_cs_testset 실녹음 wideband 100문항
> (Soniox 녹화 `runs/onedam/ev_audio`) · 원시 결과 `runs/precall/onedam/{report.md,report.json,detail.json}`, 캐시 `runs/precall/*.jsonl`(gitignore)

## 1. 요약

- 사용자 요청: "선호출을 묵음 구간이 아니라 말이 진행되고 있을 때 일정 주기로 jev로 그 이후에 의미가 바뀔 확률을 계산해서 임계값을 넘으면
  선호출을 하고 엔드포인팅이 되었을 때 선호출 결과와 최종 발화본의 정합성을 jev로 판단하는 방식으로 테스트해보고자 해"
- **이득이 작다.** 가장 나은 설정(τ 0.5, σ 0.5)에서 말하는 중 선호출이 쓰인 턴은 6%이고, 확정 뒤 LLM 대기는 평균 434 → 404ms(−30ms)로 줄었다.
  p95는 그대로 894ms다. 잘못 재사용한 경우는 0건이다. 비용은 턴당 Jev 4.2회, LLM 선호출 +0.22회다.
- 정합성 판정이 완벽해도(정답으로 판정) 상한은 16% 턴, 평균 −81ms다. 판정을 아예 빼면 22% 턴에 평균 −110ms지만, 6턴(6%)이 틀린 첫 행동을 재사용한다.
- 원인은 두 가지다. (1) Soniox 토큰이 음성보다 약 1초 늦어, 말하는 중 마지막 tick 텍스트가 최종 텍스트의 68%(p50)뿐이다.
  (2) Jev가 말하는 중에는 보수적이다(tick의 9.4%만 p ≤ 0.5). 실제로 뒤에 두 번째 질문이나 값이 붙는 문항이 많아서, 이 판단은 대체로 맞다.
- **권장: 세션에 넣지 않는다.** 기존 선호출은 그대로 둔다. 확정 뒤 첫 마디(캐시 음성)가 바로 나가므로 평균 30ms는 체감 차이가 없고,
  외부 API 의존과 호출 수만 는다.

## 2. 방식

| | 기존 | 새 방식 |
|---|---|---|
| 선호출 시점 | 침묵 200ms(그 순간 텍스트), finalize(+240ms) 텍스트가 다르면 다시 | 말하는 동안 400ms마다 Jev `meaning_will_change` ≤ τ면 그 텍스트로(응답 도착 시각에 발사) |
| 음성 재개 | 선호출 취소 | 유지(취소하지 않음) |
| 확정 때 재사용 | `match_key` 문자열 일치 | 문자열 일치면 바로, 다르면 Jev `same_reply` ≥ σ면 재사용, 아니면 기존 선호출로 폴백 |
| 정합성 판정 시각 | - | finalize 텍스트가 나온 순간 요청, 확정 뒤 도착하면 그만큼 대기(평균 2ms) |

- first: 한 번만 발사. latest: 통과할 때마다 새 텍스트로 교체. 두 모드의 결과는 거의 같아 first만 적는다.
- 재생: 녹화된 Soniox 토큰(실제 도착 시각), Silero VAD, 기존 결정기를 세션 `_process_frame`과 같은 순서로 재생했다.
  확정 시각은 `soniox_gate_eval.simulate_detector`와 같다(반올림 차이만 있음). 두 방식의 엔드포인팅은 같다.
- 정답: 선호출 텍스트와 최종 텍스트를 실제 LLM(시스템 프롬프트·툴 그대로)에 넣어 첫 행동을 비교했다. prefetch는 첫 LLM 스트림만 미리 받기 때문이다.
  - 둘 다 툴 호출이면 `tool_match` exact로 본다.
  - 둘 다 텍스트면 Claude 서브에이전트가 심사했다. 32쌍 중 31쌍이 적합했다. Gemini 대신 서브에이전트를 쓴 것은 사용자 지시다.
  - 종류가 다르면 불일치로 본다.
- 바닥값: 같은 최종 텍스트를 두 번 돌렸을 때 첫 행동 일치율은 96%(99문항)다.
- 지연 모델:
  - L은 최종 텍스트로 받은 LLM 첫 행동 시간이다. 툴이면 스트림 끝, 텍스트면 첫 이벤트까지이고, p50 764 / p95 1091ms다.
  - 확정 뒤 대기 = max(판정 대기, L − 선행 시간)
  - 선행 시간 = 확정 시각 − 선호출 발사 시각

## 3. 결과 (n=99, 확정 못 한 1문항 제외)

| 방식 | 말하는 중 선호출 재사용 | 선행 시간 p50 | 확정 뒤 LLM 대기 평균 / p50 / p95 ms | 잘못 재사용 | 놓친 재사용 | Jev/턴 | LLM/턴 |
|---|---|---|---|---|---|---|---|
| **기존 (침묵 200ms)** | - | 260 | **434 / 484 / 894** | 0 | - | 0 | 3.03 |
| 새 τ 0.3 · σ 0.5 | 4% | 260 | 419 / 481 / 894 | 0 | 3 | 4.4 | 3.10 |
| 새 τ 0.4 · σ 0.5 | 6% | 260 | 404 / 468 / 894 | 0 | 6 | 4.4 | 3.18 |
| 새 τ 0.5 · σ 0.5 | 6% | 260 | 404 / 468 / 894 | 0 | 10 | 4.2 | 3.25 |
| 새 τ 0.5 · σ 0.7 / 0.85 | 4% / 3% | 260 | 418 / 427 (평균) | 0 | - | 4.2 | 3.25 |
| (대조) τ 0.5 · 판정 없이 재사용 | 22% | 520 | 324 / 336 / 798 | **6** | 0 | 4.0 | 3.25 |
| (대조) τ 0.5 · 정답으로 판정(상한) | 16% | 460 | 353 / 403 / 798 | 0 | 0 | 4.0 | 3.25 |
| (대조) τ 0.5 · 문자열 일치만 | 0% | 260 | 434 / 484 / 894 | 0 | 16 | 4.0 | 3.25 |

- 표의 선행 시간 p50은 재사용한 모든 턴의 값이다. 말하는 중 선호출이 쓰인 6턴만 보면 417~2584ms이고, 기존은 260ms다.
- 문자열 일치만으로는 말하는 중 선호출이 한 번도 쓰이지 않는다. Soniox가 말하는 중에 내는 텍스트는 늘 최종 텍스트와 다르다. 그래서 정합성 판정이 없으면 이 방식 자체가 성립하지 않는다.

### Jev 정합성 판정 품질

- 29쌍에서 AUC 0.75다. 정답상 같은 쌍은 23개다.
- σ 0.5에서는 틀린 수락이 0건이지만 놓침이 많다.
- 놓친 쌍 대부분은 **뒤에 질문이나 정보가 더 붙지만 첫 조회는 같은** 경우다. 이때 첫 행동만 미리 받아 두면 나머지는 두 번째 LLM 회차가 최종 텍스트로 처리한다. 예:
  - q052 "하루에 몇 알 먹어" → "…한 통이면 며칠 가요?" (p 0.04)
  - q068 "콜라겐 먹으면 살쪄요?" → "…칼로리가 얼마나 돼요?" (p 0.05)
  - q093 "회사 주소가 어디예요?" → "…직접 가서 사도 돼요?" (p 0.06)
- 질문이 "응답 전체가 같은가"라서, prefetch가 실제로 필요로 하는 "첫 행동이 같은가"보다 엄격하다.
- 판정 없이 재사용하면 틀리는 6턴(q004, q011, q014, q043, q044, q058)은 모두 Jev가 거절했다. 뒤에 붙는 말이 응답을 바꾸는 경우다.
  - q004: 주문번호 뒷자리
  - q014: 쿠폰 문의 추가
  - q044: "그리고 얼마 나가요?"

### 왜 일찍 쏘지 못하나

- tick 534개 중 p ≤ 0.3은 2.8%, p ≤ 0.5는 9.4%다. 한 번이라도 0.5 이하로 내려간 문항은 99개 중 22개다.
- 말하는 중 마지막 tick 텍스트 길이는 최종 텍스트의 68%(p50), 하위 25%는 56%다. 마지막 tick부터 확정까지는 p50 0.72초다.
  즉 고객이 마지막 구절을 말할 때 텍스트는 아직 그 앞 구절이다(Soniox 토큰 약 1초 지연, AG-T30 발견 이슈).
- 기존 선호출의 선행 시간(260ms)이 짧은 것도 같은 이유다. finalize 텍스트(+240ms)가 나와야 확정 텍스트와 일치한다.

## 4. 결론과 남은 선택지

- 지금 형태로는 세션에 넣지 않는다. 기본 꺼짐 모듈로도 만들지 않았고, 평가 도구만 남긴다.
- 다시 볼 만한 변형:
  1. 정합성 질문을 "첫 조회(툴·값)가 같은가"로 바꾸고, 선호출이 실제로 낸 툴 호출을 상태에 넣는다. 상한(정답 판정)은 평균 −81ms, p95 −96ms다.
  2. 선호출 첫 행동이 텍스트면 재사용하지 않고 툴일 때만 판정한다. 텍스트 응답은 그대로 송출되므로 틀렸을 때 비용이 더 크다.
- 다만 상한도 평균 100ms 안쪽이다. 확정 뒤 대기 p50 484ms의 대부분은 L(764ms) 자체에서 온다. 더 큰 이득은 LLM 첫 행동 시간을 줄이는 쪽(AG-T15c 계열)에 있다.
