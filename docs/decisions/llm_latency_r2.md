# LLM 지연·비용 2차: 동시 요청(hedging)과 컨텍스트 캐시 (AG-T15c)

- 측정: 2026-11-19 21:54~23:42, `scripts/bench_llm_r2.py` 4회 실행. 원자료는 `runs/llm_r2/1119_2154.jsonl`, `1119_2206.jsonl`, `1119_2219.jsonl`, `1119_2339.jsonl`(로그 `runs/llm_r2_*.log`)
- **조건**: Gemini API **직접 키**(`GEMINI_API_KEY`, `make_gemini_client()`의 기본 엔드포인트)로 쟀다. BAZE 게이트웨이는 쓰지 않았고 gpt-5.4-mini도 쓰지 않았다. 측정 PC는 Windows 개발 PC이고, 요청은 한 번에 하나씩 순차로 보냈다.
- 프롬프트는 실제 `agent.prompts.build_system` 출력(규칙·매뉴얼, 약 6,900자)과 `mock_api/data/tools.json` 함수 14개다. 호출마다 `now`를 바꿔 `## 이번 통화` 접미부를 다르게 했다. 고정 접두부는 실서버처럼 모든 호출에서 같다. 입력은 호출당 약 6,400토큰이다.
- 질문 10개: 툴 7개(배송·주문 목록·취소·환불·쿠폰·상담원 연결·재고)와 툴 없음 3개(영업시간·반품 정보 부족·범위 밖). 툴 질문은 가짜 툴 결과를 넣고 후속 호출까지 잰다. 모드는 질문·라운드마다 순서를 돌려 같은 시간대에 번갈아 돌렸다. 각 실행에서 모드마다 30회다.
- 첫 이벤트는 요청부터 첫 텍스트 또는 첫 tool_call까지의 시간(초)이다. 비용은 usage_metadata의 입력·캐시·출력 토큰에 2026-11 가격표를 곱한 값이다. 3.5-flash-lite는 입력 $0.30, 캐시 $0.03, 출력 $2.50이고 3.1-flash-lite는 각각 $0.25, $0.025, $1.50이다(100만 토큰당). 동시 요청에서 취소된 쪽은 usage가 오지 않으므로, 같은 입력 토큰이 청구된다고 보고 추정해 더했다.

같은 시간대에 비교한 결과(실행 ④, 23:39~23:42, n=30):

| 모드 | 첫 이벤트 p50 | p95 | 최대 | 정확도 | 3.5 채택 비율 | 호출당 비용(¢) |
|---|---|---|---|---|---|---|
| fallback(이전 기본, 캐시 없음) | 1.25 | 3.73 | 4.33 | 29/30 | 92% | 0.248 |
| **hedge 500ms + 캐시(채택)** | **1.20** | **1.64** | **1.84** | **30/30** | 84% | **0.074** |

- **꼬리 지연**: fallback은 3.5가 막히면 2.5초를 기다린 뒤에야 3.1로 넘어가므로 3.7~4.3초가 된다. hedge 500ms는 0.5초 뒤 3.1을 동시에 시작하므로 꼬리가 약 1.6~1.9초로 잘린다.
- **비용**: 캐시로 입력 6,400토큰 중 6,245토큰이 캐시 단가(1/10)로 청구된다. 3.5-flash-lite는 첫 이벤트 p50이 1.1초 안팎이라 500ms hedge는 거의 항상 발동한다(30/30). 그래도 대체 모델의 입력도 캐시 단가라 추가 비용이 작다. 이전 기본(fallback, 캐시 없음)보다 **호출당 약 70% 싸다**.
- **race가 아닌 hedge 500ms를 고른 이유**: race는 p95가 0.3초 더 짧지만 3.1-flash-lite가 절반 가까이를 처리한다(47~73%). 이번 질문 세트에서는 두 모델 정확도가 같았다. 하지만 AG-T04(`bench_providers.md`)에서 3.1은 툴 대신 되묻는 경향이 있었고(5/7), round1의 응대 점수 하락 원인 후보에도 "폴백 모델 의존"이 있었다. 500ms를 먼저 주면 3.5가 84%를 처리하고 꼬리는 race와 거의 같다. `LLM_MODE=race`로 바로 바꿀 수 있다.
- 서버 연결: `server.py`·`config.py`는 바꾸지 않았다. `build_deps`가 찾는 `make_llm_with_fallback`이 `LLM_MODE`에 따라 HedgedLLM, FallbackLLM 또는 단일 모델을 돌려준다. HedgedLLM은 FallbackLLM을 상속하므로, 서버 예열(`llms` 순회, 404 모델 제외)과 기존 isinstance 검사가 그대로 동작한다.

## 2. 컨텍스트 캐시

### 2.1 공식 문서 확인 (aistudio.google.com/docs/caching, /docs/pricing, 2026-11-19)
- 암시적 캐시는 Gemini 2.5 이상에서 자동으로 켜진다. 문서의 최소 토큰 표에는 flash-lite 행이 없다(3.8/3.6 Flash 4096, 2.5 Flash 2048). 할인율도 적혀 있지 않다. 캐시 적중은 usage_metadata에서 확인한다.
- 명시적 캐시는 Gemini 3과 2.5의 generateContent에서 쓸 수 있고 Gemini 4에서는 미지원이다. TTL을 정하지 않으면 1시간이다.
- 가격: 캐시 입력은 3.5-flash-lite $0.03/1M, 3.1-flash-lite $0.025/1M로 일반 입력의 1/10이다. 저장은 두 모델 모두 $1.00/1M토큰/시간이다. 무료 티어에서는 캐시를 쓸 수 없다.

### 2.2 실측으로 확인한 사실
| 항목 | 결과 |
|---|---|
| 명시적 캐시 최소 크기(3.5-flash-lite) | 1024토큰. 806토큰은 400 `Cached content is too small. total_token_count=806, min_total_token_count=1024`, 1849토큰은 생성됐다(3.1도 1849 OK) |
| 우리 접두부 크기 | 고정 규칙·매뉴얼 + 툴 14개 = **5,767~6,245토큰**(모델·버전별). 최소 크기를 넉넉히 넘는다 |
| 생성 시간 | 2.0~2.3초. 첫 요청은 기다리지 않고 백그라운드에서 만든다 |
| 요청 제약 | `cached_content`를 쓰는 요청에 `system_instruction`, `tools`, `tool_config`를 함께 주면 **400**(`CachedContent can not be used with GenerateContent request setting system_instruction, tools or tool_config`). 그래서 가변 접미부는 contents로 옮겨야 한다 |
| 암시적 캐시 | 동작은 하지만 불안정하다. 같은 요청을 반복하면 5,912토큰 중 2,016토큰이 적중했다. 다른 세션(접미부만 다름)의 첫 호출은 대개 0이었고, 같은 세션의 후속 호출은 약 4,032토큰이 적중했다. 모드별 평균 적중은 135~4,039토큰이다 |
| 명시적 캐시 적중 | 호출마다 **6,245 / 약 6,400토큰**이 캐시 단가로 청구됐다(적중률 97%) |
| 지연 | 단일 3.5 기준 p50이 **+0.07~0.24초**(1.13 → 1.24, 1.15 → 1.22, 1.11 → 1.35)이고, 3.1도 1.42 → 1.54초였다. 빨라지지 않았다. 꼬리는 캐시와 무관하게 시간대에 따라 변한다 |
| 비용 | 3.5 단일 0.258 → 0.052¢(-80%), 3.1 단일 0.126 → 0.043¢(-66%), hedge 0.389 → 0.07~0.09¢ |
| 저장 비용 | 약 6.2천 토큰 × 모델 2개 × $1/1M/시간 = **시간당 약 $0.0125**. 172문항 측정(LLM 약 300회)에서 아끼는 금액은 약 $0.5다. 시간당 호출이 대략 8회를 넘으면 이득이다 |

### 2.3 접미부 배치가 정확도를 바꾼다
- 첫 구현은 접미부(`## 이번 통화`: 시각, "발신 고객 정보: 없음 … 번호를 물어본다", 첫 마디)를 고객 첫 발화와 같은 user 메시지의 앞 파트로 넣었다. 그러자 **재고 문의("무선 이어폰 에어핏 재고 있어요?")에도 번호부터 묻는 일**이 크게 늘었다. 실행 ①·②의 캐시 모드에서 재고 질문은 21건 중 13건 실패했고, 캐시 없는 모드는 27건 중 1건 실패였다. 지시가 고객 발화 바로 옆에 붙으면서 지나치게 두드러진 것으로 보인다.
- 비교(3.5-flash-lite, 질문 3개 × 8회): 접미부를 **별도 user 턴(`[상담 시스템 안내 — 고객 발화 아님]` 머리말) + model 확인 턴("네, 이번 통화 정보를 확인했습니다.")**으로 앞에 두니 재고 8/8이었다. 같은 파트에 넣으면 3/8, 캐시가 없으면 8/8이었다. 상담원 연결과 배송 조회는 세 방식 모두 같은 답을 냈다(시각에 따라 transfer와 callback이 똑같이 갈렸다).
- 그래서 별도 턴 방식으로 바꿨다(`gemini_llm._with_suffix`). 실행 ③·④의 캐시 모드 정확도는 30/30, 30/30, 29/30, 29/30(1건은 시간 초과), 30/30, 30/30이다.
- 남은 차이: 캐시 요청에서는 '이번 통화' 정보가 system이 아니라 대화 앞부분에 놓인다. 응대 품질(judge) 영향은 아직 재지 않았다. 다음 172문항 측정에서 judge로 확인해야 한다. 문제가 보이면 `LLM_CONTEXT_CACHE=0`으로 끈다.

### 2.4 구현 (`agent/providers/llm_cache.py`)
- `split_system`: system을 첫 `## 이번 통화` 마커에서 (고정 접두부, 가변 접미부)로 나눈다. 마커가 없으면 캐시를 쓰지 않는다. 서버 예열 요청("한 단어로만 답하세요.")도 마커가 없어 캐시를 쓰지 않는다.
- 키는 sha256(모델, 접두부, 툴 정의)이다. 접미부가 달라도 같은 캐시를 쓰고, 캐시는 모델별로 따로 만든다.
- `ContextCache.lookup`은 동기로 즉시 반환한다. 캐시가 없으면 백그라운드로 생성하고 이번 요청은 캐시 없이 보낸다. 추정 토큰(UTF-8 바이트 ÷ 4, 한국어 실측 약 4.1바이트/토큰)이 1024 미만이면 만들지 않는다. 생성에 실패하면 10분 동안 다시 시도하지 않는다.
- GeminiLLM은 캐시가 있으면 `cached_content`만 주고 system_instruction과 tools를 뺀다. 접미부는 별도 턴으로 넣는다. 캐시 관련 오류(만료, 삭제, 권한)가 나면 캐시를 버리고 같은 요청을 캐시 없이 다시 보낸다.
- 서버를 끝내도 캐시는 TTL(1시간)까지 남아 저장 비용이 든다. 측정 스크립트는 끝에 `ContextCache.aclose()`로 지운다.
- **주의**: `agent/prompts.py`가 `## 이번 통화` 제목을 바꾸거나 가변 정보를 그 앞으로 옮기면 캐시가 조용히 꺼지거나(마커 없음) 세션마다 새 캐시가 생긴다. 프롬프트를 바꿀 때 `llm_cache.DEFAULT_MARKERS`도 함께 확인해야 한다.

## 3. 동시 요청 구현 (`agent/providers/hedged_llm.py`)
- `HedgedLLM(llms, hedge_delay_s, mode)`는 FallbackLLM을 상속한다. llms[0]이 기본 모델, llms[1]이 동시 요청 대상이고 llms[2:]는 순차 폴백이다.
- 텍스트·tool_call·done 가운데 **첫 이벤트를 먼저 낸 쪽**을 채택하고 다른 쪽은 태스크를 취소하고 aclose한다. 첫 이벤트 뒤에는 전환하지 않는다. 기본 모델이 h 전에 오류를 내면 바로 대체 모델을 시작한다. 둘 다 실패하면 llms[2:]를 차례로 시도하고, 그래도 안 되면 마지막 예외를 올린다.
- **툴 후속 라운드 고정**: 채택된 스트림이 낸 tool_call id에 그 모델을 기억해 둔다. 마지막 메시지가 툴 결과이고 그 호출을 낸 모델을 알면 그 모델에만 보낸다. thought_signature는 GeminiLLM 인스턴스가 모델별로 갖고 있기 때문이다. 고정 모델이 오류를 내거나 2.5초 안에 첫 이벤트가 없으면 다른 모델로 넘긴다. 이 경우 GeminiLLM은 모르는 호출 id에 공식 우회 서명을 붙인다. 측정에서 고정 라운드는 모드마다 17~21회였고 400 오류는 0건이었다.
- 새 고객 발화 턴은 고정하지 않는다(다시 hedge한다).
- 세션 선호출을 취소(aclose)하면 진행 중인 두 스트림이 모두 닫힌다(테스트로 확인).
- 통계 `stats`: `served:<모델>`, `hedge:<대체>`, `pinned:<모델>`, `error:<모델>`. 사용량은 `GeminiLLM.usage_totals`, `on_usage` 콜백에서 볼 수 있다.

## 4. E2E (smoke 20문항, mock 8104 / agent 9104, 23:44~23:52)
- A = `LLM_MODE=fallback LLM_CONTEXT_CACHE=0`(이전 동작), B = 새 기본값(hedge 500ms + 캐시). 두 실행 모두 BAZE를 끈 `.env`로 서버를 새로 띄웠다(STT gemini live, LLM은 Gemini 직접 키). A를 먼저 돌리고 약 5분 뒤 B를 돌렸다(`--concurrency 2`). 원자료는 `runs/llm_r2_e2e/{A1,B1}/`(턴 로그 `logs/`)이고, 스크립트는 메인 세션의 `runs/run_baseline.sh`와 같은 순서(mock → agent → eval.runner → eval.score)다.

- 본 응답 공백과 turn.end는 크게 줄었다. 공백 p90은 2.2초에서 0.2초로, turn.end p50은 5.9초에서 3.7초로 줄었다. 안전 상한(20초)과의 여유도 커졌다(최대 9.5초 → 6.9초).
- 속도 점수와 말 끝 전 발화(4 → 5)는 턴 결정기·VAD 쪽 편차다. 첫 소리는 캐시 첫 마디라 LLM과 무관하다. 함수 정확률은 20문항에서 1문항 차이다. 표본이 작아 함수·속도 차이는 판단하지 않는다.
- 서버 예열이 HedgedLLM 체인에서 404인 `gemini-2.5-flash-lite`를 뺐다(`llm_chain: [3.5, 3.1]`). 캐시는 3개가 만들어졌다. 3.5와 3.1의 접두부+툴 캐시(각 6,245토큰)와, 마지막 툴 회차(툴 없이 호출) 요청용 3.5 접두부 전용 캐시(4,305토큰)다. 마지막 회차는 tools가 비어 키가 달라진다.

## 5. 측정 중 이상
- 실행 ③에서 순차 측정 중 두 호출이 `asyncio.timeout(20초)`를 훨씬 넘겨 각각 3,940초와 146초 뒤에 끝났다. 둘 다 단일 모델 모드(GeminiLLM 직접 호출, HedgedLLM 아님)였고, 그 사이 다른 기록이 전혀 없다. 야간에 PC가 절전에 들어갔다가 깨어난 것으로 추정한다. 해당 2건은 시간 초과로 셌고 p50·p95에는 영향이 거의 없다. 이 실행의 전체 시간 78분은 이 때문이다.
- `.env`에 `BAZE_API_KEY`가 있으면 factory의 `make_llm`이 `LLM_PROVIDER=auto`에서 OpenAI(gpt-5.4-mini, BAZE 경유)를 기본 LLM으로 고른다. 이 측정 뒤 메인 세션이 BAZE를 껐다(크레딧 소진). 다시 켜면 hedge는 "gpt-5.4-mini + gemini-3.1-flash-lite" 조합이 되므로 기본 LLM을 확인해야 한다.
