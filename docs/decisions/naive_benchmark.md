# 단순 STT+LLM+TTS 조합 벤치마크 (AG-T13)

- 목적: 우리 최적화(보정 턴 결정기, 캐시 첫 마디, 선호출, 문장 단위 TTS, 정규화·번호 교정, 튜닝 프롬프트, LLM 폴백)가 점수를 얼마나 만들었는지 보이기 위한 **기준선(naive)**.
- 같은 172문항(`data/testset`), 같은 측정기(`eval.runner --concurrency 4`), 같은 채점기(`eval.score`), 같은 Mock API.
- 코드: `bench/naive_server.py`(`uv run python -m bench.naive_server --port 9000 [--tts-mode sentence]`), 실행 `bash bench/run_naive.sh [이름] [full|sentence]`, 테스트 `tests/test_naive_server.py`.
- 원자료: `runs/naive_172_2036`(N0, judge 포함), `runs/naive_n1_172_2046`(N1), `runs/round1_172_2003_judge`(round1 결과에 judge만 새로 적용한 사본. 원본 `round1_172_2003`은 손대지 않음).

## 단순 조합 정의 (흔한 최소 구현, 일부러 망가뜨리지 않음)

| 부품 | N0 (순수 단순 조합) | round1 (우리) |
|---|---|---|
| STT | gemini-3.5-transcribe-live(factory `make_stt`), 숫자 복원·재인식 래퍼 끔 | 같은 모델 + 부분 결과 숫자 복원 |
| 말 끝 | Silero VAD(p≥0.5), 연속 200ms 음성이면 발화 시작, **고정 침묵 800ms**(Starter Kit 예시 서버 값) | Silero + 텍스트 규칙 × 발화 길이 보정 표 |
| 말 끝 뒤 | STT finalize → 최종 텍스트 | 침묵 200ms에 finalize·LLM 선호출 |
| 첫 소리 | 본 응답 TTS의 첫 음성 | 캐시 첫 마디(상황별 3종) 확정 즉시 송신 |
| LLM | gemini-3.5-flash-lite(`make_llm`), **폴백 없음** | 같은 모델 + 3.1-flash-lite 폴백(첫 이벤트 2.5초) |
| 프롬프트 | 짧은 역할 3문장 + `cases/manual.md` + now·caller·history JSON 원문 | 튜닝 규칙(함수 사용·인계·되묻기·숫자 읽기 등) + 매뉴얼 |
| 함수 | GET /tools 그대로, `X-Session-Id`, 인자 그대로, 최대 3회차(마지막은 툴 없이) | 인자 정규화·번호 교정·자릿수 검사·인계 안전망 |
| TTS | edge SunHi, **전체 응답 텍스트로 1회**, 받는 대로 송신(앞 무음 제거·레벨 정규화 없음) | 문장 단위 스트리밍, 첫 문장 선합성, 레벨 정규화 |
| 순서 | PCM → agent.transcript → turn.end → drain, 에러여도 turn.end(말 끝 뒤 22초 안전 상한) | 같음 |

N1 = N0 + 문장 단위 스트리밍 TTS만(LLM 텍스트에서 문장 끝이 나오면 바로 합성·송신).

## 해석

1. **속도 점수(30%)는 거의 전부 캐시 첫 마디 + 턴 결정에서 나온다.** 단순 조합은 "고정 800ms + finalize + LLM 전체(함수 회차 포함) + TTS 첫 바이트"를 기다리므로 첫 소리 p50이 5초, 1.5초 안에 든 문항은 8개뿐이다(round1 138개). 속도 점수 85.6 → 25.2, 추정 총점 기준 약 **18점**(속도 60점 차 × 0.3)이 여기서 갈린다.
2. **말 끝 전 발화는 단순 조합이 더 적다(8 vs 23). 하지만 잘 끊어서가 아니라 응답이 늦어서다.** 단순 조합도 쉼에서 일찍 끊는다. STT 텍스트가 실제 발화의 60% 미만인 문항이 22건(mid_pause 11, digits 8, connective_end 7)이다. 다만 응답이 5초 뒤에 나오니 그때는 고객 말이 이미 끝나 있어 0점이 되지 않는다. 대신 부분 발화로 답하므로 함수·응대 점수를 잃는다. round1은 첫 마디를 즉시 내보내므로 잘못 끊으면 그대로 0점이 된다. 그래서 round1에서는 턴 결정기 품질이 직접 점수가 된다.
3. **함수 점수(20%)는 정규화·번호 교정·프롬프트 규칙이 +8.7점(65.7 → 74.4)을 만들었다.** 차이가 큰 곳은 실행(50.0 → 64.7), 불만·인계(35.3 → 52.9: transfer_to_agent가 필요한 16문항에서 실제 호출 8 → 10, 단순 조합은 연결을 말로만 하는 일이 있다), 조회(62.8 → 73.1), 정보 부족(71.1 → 89.5: 기대하지 않은 함수 호출 5 → 2건, 번호 없이 함수를 부르지 않는 규칙)이다. FAQ·범위 밖은 둘 다 100.
4. **응대(judge)는 단순 조합이 오히려 높다(64.8 vs 60.4).** 원인은 다음과 같다.
   - round1의 말 끝 전 발화 23건 중 16건이 응대 0점이다(부분 발화로 답함). 말 끝 전 발화를 빼면 round1 66.0 vs N0 67.7로 거의 같다.
   - round1의 "번호를 한 자리씩 천천히 다시 말씀해 주시겠어요?" 되묻기가 16건이다(자릿수 검사·번호 교정이 STT 숫자 오인식을 막는 대신, 안내해야 할 내용을 빠뜨린다). 단순 조합은 0건으로, 틀린 번호로도 일단 조회한다.
   - round1 측정 시간대에 flash-lite가 혼잡해 대부분의 호출이 3.1-flash-lite 폴백으로 처리됐다(폴백 경고 348회). 단순 조합은 3.5-flash-lite만 썼다. 모델 차이가 응대에 섞여 있다.
   - judge는 텍스트만 본다. 첫 마디 뒤 공백, 인사 반복(N0는 "안녕하세요, 다이렉트몰 고객센터입니다"를 59건에서 매번 반복), 마크다운(1건)은 감점되지 않는다.
   → 응대 점수에는 튜닝 프롬프트의 효과가 아직 드러나지 않는다. 오프라인에서는 69.5 → 73.0이었다. 응대를 올리려면 (a) 말 끝 전 발화 감소, (b) 번호 되묻기를 조건부로 완화(조회 결과가 not_found일 때만 되묻기), (c) 폴백 의존 감소가 필요하다.
5. **문장 단위 TTS(N1)만으로는 거의 얻는 게 없다.** 같은 실행 안에서 비교하면 "LLM 완료 → 첫 소리"가 1.57s → 1.34s로 약 0.2초 줄 뿐이다. Gemini 스트림이 큰 덩어리로 오고, 대부분의 시간은 LLM 첫 토큰과 함수 회차가 차지한다. N1 실행 시간대에는 LLM이 더 혼잡했다(LLM 완료 p50 3.35 → 5.34s, 안전 상한 도달 4 → 11건). 그래서 N1의 전체 수치는 N0보다 나쁘게 나왔지만 이는 시간대 차이다. 문장 단위 TTS는 **캐시 첫 마디와 함께 쓸 때** 본 응답 공백을 줄이는 보조 장치다.
6. **LLM 폴백도 꼬리를 줄인다.** 폴백이 없는 단순 조합은 혼잡 시 응답이 22초 안전 상한까지 걸리는 문항이 4~11건 나왔다(turn.end p95 17~23s). round1은 폴백 덕분에 p95가 10.5s다.
