# STT 튜닝 (AG-T10b)

- 측정: 2026-11-19 · Windows 개발 PC · `GEMINI_API_KEY`(무료 티어 한도 적용) · 실시간 속도(1.0x), 동시 4(재인식 실험은 3)
- 도구: `eval/stt_eval.py`(새). 문항 오디오를 20ms씩 실시간으로 STT 스트림에 흘리고, **말 끝(meta.speech_end) + 침묵 200ms** 지점에서 `finalize()`(세션의 선호출 시점과 같음). finalize 동안에도 남은 꼬리 오디오를 계속 보낸다.
- 세트: 본 테스트셋 172문항(`data/testset/audio`, Gemini 목소리 125·edge 47), digits 태그 54문항, short 태그 31문항, 스모크 20문항(`data/testset/smoke/audio`, edge 목소리만)
- 원시 결과: `runs/stt_eval/<실행 이름>/{rows.jsonl,summary.json,report.md}`(gitignore 영역). 재현 명령은 맨 아래.

## 지표 정의

| 지표 | 정의 |
|---|---|
| CER | 정답 텍스트(`customer_utterance`) 대비 글자 편집거리 / 정답 길이. 공백·문장부호 제거 |
| CER(숫자정규화) | 양쪽의 숫자 토큰(한글 낭독 "이육일일", 아라비아 숫자, `010-1234-5678`)을 숫자열로 바꾼 뒤 CER. 원문 CER은 낭독 vs 숫자 표기 차이 때문에 의미가 적다 |
| 숫자 정확도 | digits 태그 문항만. 기대 함수의 키 인자(order_id·phone_number)가 STT 결과의 이어진 숫자열(`stt_recheck.digit_runs`, `agent.normalize` 규칙)과 **정확히 같으면** 정답. 정정 발화처럼 정답 인자가 정답 텍스트에 이어 읽혀 있지 않거나 기대 함수가 없으면(번호를 덜 말한 문항) 정답 텍스트의 숫자 전체를 그대로 재현했는지로 판정 |
| finalize 지연 | `finalize()` 호출 → 반환(재인식 래퍼가 있으면 재인식 시간 포함) |
| 말 끝 빈 부분결과 | 말 끝 순간 `latest_text()`가 빈 문항 비율 |
| finalize 시점 빈 부분결과 | 말 끝 + 200ms(선호출 시점)에 빈 비율 |
| 첫 부분결과 | 음성 시작(lead_ms)부터 `latest_text()`가 처음 비지 않게 된 시각 |

## 실험

### 1. Live 설정 (digits 54문항)

| 실행 | 설정 | CER(숫자정규화) | 숫자 정확도 | finalize p50/p95 |
|---|---|---|---|---|
| d_base2 | 기본(ko-KR, 모드 미지정) | 0.051 | 74.1% | 429 / 553 |
| d_verbatim | `mode=VERBATIM` | 0.051 | 74.1% (결과 텍스트가 기본과 문항별로 동일) | 423 / 556 |
| d_vocab | `custom_vocabulary=주문번호,휴대폰 번호,전화번호,공일공,번호는` | 0.054 | 72.2% | 429 / 524 |
| d_smart | `mode=SMART`(숫자·목록 서식화) | 0.161 | **59.3%** | 420 / 552 |
| d_auto | `language_codes=[]`(자동 감지) | 0.114 | **44.4%** | 419 / 763 |
| d_c50 | 묶음 50ms | 0.051 | 74.1% | 411 / 503 |

- 공식 문서(Live Transcribe 가이드) 확인 결과 설정 가능한 것은 `language_codes`, `custom_vocabulary`(≤1000, 권장 ≤100), `mode`(VERBATIM 기본/SMART), `source_text`(SMART 전용), 서버 VAD(`realtime_input_config.automatic_activity_detection`), 묶음 100ms(1024~2048프레임) 권장. **transcribe-live는 시스템 지시를 받지 않는다**(Live Agent 기능 목록에만 있음) → "숫자는 한 자리씩" 같은 지시를 넣을 경로가 없다. 부분 결과(`interim_input_transcription`)는 별도 설정 없이 항상 온다(켜는 플래그 없음).
- 결론: **ko-KR + 기본 모드가 최선.** 어휘 힌트는 이득 없음(숫자 자체는 어휘로 편향할 수 없다), SMART·자동 감지는 크게 나쁘다. 같은 오디오·설정이면 결과가 거의 결정적이다(d_base2 = d_verbatim 문항별 동일). 다만 실행마다 1문항 정도 흔들린다(T0093·T0105).
- 서버 VAD 설정은 finalize를 `audio_stream_end`(hybrid VAD, 문서 권장)로 하므로 영향이 없어 실험하지 않았다(env 노브만 추가).
- `gemini-3.8-live`는 TEXT 응답 모드에서 전사 이벤트를 하나도 주지 않았고, `gemini-3.1-flash-live-preview`는 TEXT 모드를 거부(1007)했다. 두 모델은 대화형(오디오 응답) 모델이라 전사 전용으로 쓰기 어렵다.

### 2. 부분 결과(latest_text)가 비는 원인

- **AG-T09a의 "확정 시점 텍스트가 빈 턴 7/20"은 오독이었다.** 결정기 로그의 `text=neutral:+0.0`은 "텍스트 규칙이 중립"이라는 뜻이지 텍스트가 비었다는 뜻이 아니다. 실제 턴 로그(`runs/logs/turns-20261119.jsonl` 215턴)에서 최종 선호출 시점에 텍스트가 없어 선호출을 못 한 턴은 **18/215(8.4%)**로, 이 평가기의 말 끝 빈 비율(7~8%)과 같다.
- 빈 문항은 **모두 음성 길이 1.32초 이하의 짧은 발화**다(12/12). 첫 부분 결과가 음성 시작부터 p50 1.1초, p95 1.7초에 오고, 이후 부분 결과는 약 0.5초 간격·0.4~0.5초 지연으로 갱신된다(이벤트 타임라인: `rows.jsonl`의 `events`, `GeminiLiveStream.events`에 기록하도록 추가). 수신 처리(`_handle`)에는 버그가 없다.
- 묶음 크기 실험(short 31문항, 말 끝 빈 문항 수): 100ms 13·50ms 10·40ms 11·200ms 14, 172 전체 실행에서는 100ms 11·50ms 12. 첫 부분 결과는 50ms가 약 0.1초 빠르지만 빈 비율 차이는 실행 간 흔들림(±2문항) 안이다 → **문서 권장 100ms 유지.**
- 따라서 짧은 발화의 말 끝 텍스트 공백은 서버 쪽 첫 부분 결과 지연(~1.1초)이 원인이고 STT 설정으로는 줄지 않는다. 결정기·선호출 쪽에서 "텍스트 없음"을 정상 상태로 다뤄야 한다(턴 로직 Task로 넘김. 예: 짧은 발화의 빈 텍스트는 neutral이 아니라 짧은 답 가능성으로, 또는 finalize 결과(+~0.4초)를 결정에 반영).

### 3. 숫자 보정 2차 경로 (batch 재인식)

`DigitRecheckSTT`(`agent/providers/stt_recheck.py`): finalize 결과에 6자리 이상 숫자열이 있는데 10자리도, 01로 시작하는 11자리도 아니면 발화 오디오 전체를 batch 모델로 다시 받아쓰고, 재인식 결과에 기대 자릿수 숫자열이 더 많을 때만 교체한다. 172문항 기준 트리거 17건(9.9%) — 실제 숫자 오답 15건 중 12건을 잡고, 맞았는데 트리거되는 것은 정정 발화 3건(T0062·T0127·T0167, 교체되지 않음)과 비-digits 1건.

재인식 모델 단독 비교(오디오 = 말 끝+200ms까지, digits 54 또는 어려운 18문항):

| 모델 | 대상 | 숫자 정확도 | 지연 p50 / p95 | 비고 |
|---|---|---|---|---|
| `gemini-3.5-transcribe` | digits 54 중 10건만 성공 | 10/10 | 2346 / 2677ms | **하루 100요청 한도**(429, `GenerateRequestsPerDayPerProject…`, 같은 키를 다른 작업과 공유) — 쉬운 문항만 표본, 어려운 문항은 측정 못 함 |
| `gemini-3.5-flash-lite` (thinking MINIMAL) | digits 54 | 33.3% | 1904 / 2390ms | 첫 프롬프트의 예시 번호(2611150231)를 그대로 베껴 씀 → 예시 제거 |
| `gemini-3.5-flash-lite` (새 프롬프트) | 어려운 18 | 27.8% | 1538 / 2421ms | |
| `gemini-3.1-flash-lite` (MINIMAL) | 어려운 18 | 27.8% | 1810 / 2137ms | |
| `gemini-3.5-flash` (MINIMAL) | 어려운 18 | 33.3% | 2105 / 2656ms | |

어려운 18문항 = live가 틀린 15 + 정정 3. flash 계열도 "이육일일"을 "유기를/이유기를/EU"로 듣는다 — live만의 문제가 아니라 **음성 자체(특히 edge 목소리 + 통화 채널)의 문제**다.

래퍼 E2E(digits 54, 재인식 제한 3초):

| 실행 | 재인식 모델 | 트리거 | 교체 | 고침 | 망침 | 시간 초과 | 재인식 지연 p50 / 최대 | 숫자 정확도 | finalize p95 |
|---|---|---|---|---|---|---|---|---|---|
| d_c50 | (없음) | - | - | - | - | - | - | 74.1% | 503ms |
| d_c50_rc35 | 3.5-flash-lite | 15 | 2 | 0 | 0 | 2 | 2144 / 3007ms | 74.1% | 2896ms |
| d_c50_rc31 | 3.1-flash-lite | 15 | 2 | 1 | 0 | 1 | 2377 / 2984ms | 75.9% | 3094ms |

- **지연 비용**: 재인식은 트리거된 턴(약 10%)에서 finalize 뒤 **+1.5~3.0초**. 세션은 finalize를 침묵 200ms에 시작해 확정 뒤 `finalize_timeout_s + 0.5`(1.5초)까지만 기다리므로, 재인식이 쓸모 있으려면 약 1.3초 안에 끝나야 한다 → **1.3초 안에 끝난 재인식 0/30.** 기본 세션 설정으로는 재인식 결과가 거의 항상 버려지고(시간 초과 → 원래 결과), `DIRECTON_FINALIZE_TIMEOUT_S`를 늘리면 본 응답이 그만큼 늦어진다.
- **판단: batch 재인식은 기본 끔(`STT_DIGIT_RECHECK=0`).** 얻는 것(54문항 중 0~1건) 대비 본 응답 +2초가 크다. 첫 마디가 캐시라 속도 점수엔 영향이 없지만 첫 마디 뒤 공백(지금도 ~0.9초)이 3초로 늘어 응대 품질이 나빠진다.

### 4. 부분 결과 숫자 복원 (채택, 추가 지연 0)

이벤트 타임라인을 보니 **부분 결과에선 맞던 숫자가 확정에서 틀어지는 경우**가 있었다(T0105: 부분 `2611 180042` → 확정 `26111800042`). 래퍼가 finalize 직전 `latest_text()`를 기억했다가, 확정 결과에 틀린 자릿수 숫자열이 정확히 하나 있고 직전 부분 결과에 확정에 없는 맞는 자릿수 숫자열이 정확히 하나 있으면 그 숫자열만 바꾼다(꼬리 말은 확정 결과 유지). 네트워크 호출이 없어 지연 0. 172문항 중 1건 교체·1건 고침, 망친 것 0. 효과는 작지만 비용·위험이 없어 기본 켬.

## 채택 설정

| 항목 | 값 | 환경변수(끄기/바꾸기) |
|---|---|---|
| STT 모델 | `gemini-3.5-transcribe-live` (실패 시 batch 폴백, 기존과 같음) | `GEMINI_STT_LIVE_MODEL` |
| 언어 | `ko-KR` (자동 감지 금지) | `STT_LANGUAGE` (`auto`면 자동 감지) |
| 모드 | 미지정(서버 기본 VERBATIM). SMART 금지 | `STT_LIVE_MODE` |
| 묶음 | 100ms | `STT_LIVE_CHUNK_MS` |
| 기본 어휘 | 없음 | `STT_VOCABULARY`(쉼표 구분), 세션별은 기존 `DIRECTON_STT_CONTEXT` |
| 서버 VAD | 서버 기본(finalize는 `audio_stream_end`) | `STT_VAD_SILENCE_MS`, `STT_VAD_END_SENSITIVITY`(LOW/HIGH) |
| 부분 결과 숫자 복원 | **켬** (factory가 `DigitRecheckSTT`로 감쌈) | `STT_DIGIT_INTERIM_FIX=0` |
| batch 재인식 | **끔** | `STT_DIGIT_RECHECK=1`, `STT_RECHECK_MODEL`(기본 `gemini-3.5-flash-lite`), `STT_RECHECK_TIMEOUT_S`(기본 1.5) |

- session.py는 고치지 않았다(재인식·복원 모두 `finalize()` 안에서 끝난다). batch 폴백 스트림(`GeminiBatchStream`)은 감싸지 않는다.

## 남은 문제

1. **끊어 읽은 숫자 정확도 74%(통화 채널 63~71%, edge 목소리 54%, 스모크 12.5%)가 STT 설정으로는 오르지 않는다.** live·batch·flash 모두 같은 구간("이육일일")을 못 듣는다. 남은 수단:
   - LLM 쪽: 자릿수가 10/11이 아니면 반드시 되묻기 + 되물을 때 "한 자리씩 천천히" 유도(프롬프트 Task). 되묻기 응답은 대개 짧고 또렷해 2턴째에 맞을 가능성이 높다.
   - Soniox(`SONIOX_API_KEY`, AG-U01) 같은 다른 STT 실측 비교 — 키가 생기면 `uv run python -m eval.stt_eval --tags digits --stt soniox ...`로 바로 비교 가능.
   - `gemini-3.5-transcribe`를 어려운 문항에 재측정(한도 회복 뒤). 쉬운 문항 10/10이었지만 지연 2.3초 + 하루 100요청이라 실시간 경로엔 부적합.
   - 테스트 음성 쪽: edge 목소리의 숫자 낭독이 유난히 어렵다. 대회 실제 음성이 사람 목소리라면 정확도가 다를 수 있다 → 사람 녹음 몇 개로 확인 권장.
2. **짧은 발화(≤1.3초)는 말 끝 순간 부분 결과가 없다**(첫 부분 결과 ~1.1초, 서버 쪽). 결정기·선호출이 빈 텍스트를 전제로 동작하게 하는 턴 로직 수정이 필요하다(다른 Task).
3. **선호출 재사용률이 낮은 원인은 빈 텍스트가 아니라 텍스트 불일치**다: 침묵 200ms의 부분 결과는 마지막 단어가 덜 나온 상태(0.4~0.5초 지연)라 finalize 결과와 거의 항상 다르다(예: "…주소도 바꿀 수" vs "…바꿀 수 있나요?"). 세션의 비교 규칙(정확 일치)을 완화하는 것은 턴/세션 Task 범위.
4. 실행 간 흔들림이 문항 1개 정도(54문항 중 ±1.9%p) 있다. 1~2문항 차이는 결론에 쓰지 말 것.
5. 평가기 숫자 판정은 이어진 숫자열 정확 일치라, "2611 180 아 잠깐만요 160457" 같은 정정은 정답 텍스트의 숫자 전체 재현으로 본다(LLM이 정정을 올바르게 합치는지는 별개).
