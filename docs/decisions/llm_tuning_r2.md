# LLM 응대 2차 튜닝: 번호 되묻기 조건부 완화 + 응답 내용 보강 (AG-T15a)

- 측정: 2026-11-19 · 오프라인 평가기 `eval/llm_eval.py`(실제 프롬프트 + 실제 Responder 툴 루프, Mock 직접 호출) · 심사 `gemini-3.8-flash`(eval.score 심사 함수)
- 배경(`naive_benchmark.md`): judge 기준 응대 점수가 round1 60.4 < 단순 조합 64.8. round1의 "번호를 한 자리씩 다시 말씀해 주시겠어요?" 되묻기 16건(단순 조합 0건), 2~3문장 제한 때문에 기대 항목 누락(llm_tuning.md: tool_lookup 59 정체).
- 원시 결과: `runs/llm_eval_r2_*`(아래 표마다 실행 이름), 로그 `runs/llm_eval_r2_*.log`.

## 1. 평가 방법: STT 텍스트 모드(새로 추가)

정답 텍스트로는 STT 숫자 오인식이 안 나타나서 되묻기 정책을 비교할 수 없다. `eval/llm_eval.py`에 `--stt-text <파일>`을 추가했다.

- 문항별 실제 STT 최종 텍스트를 LLM 입력(고객 발화)으로 쓴다. 심사·기록의 `customer_utterance`는 정답 그대로 두고, 행에 `input_utterance`(실제 입력)·`stt_missing`(STT가 없어 정답으로 대체)을 남긴다.
- 파일 형식 자동 판별: `runs/stt_eval/*/rows.jsonl`(case_id + final), 세션 턴 로그 `runs/logs/turns-*.jsonl`(session_id + user_text, `--stt-sessions runs/<측정 실행>`으로 그 실행의 세션만), `{case_id: text}` JSON.
- 되묻기 응답 수(`reprompts`: "다시/한 번 더 말씀", "한 자리씩")를 행·요약에 넣었다. `--compare`에도 나온다.
- **기준 STT 텍스트로 `runs/stt_eval/final_full/rows.jsonl`을 썼다**(채택 STT 설정, 말 끝 + 200ms에 finalize한 전체 발화 결과, 172/172). round1 턴 로그(`turns-20261119.jsonl`의 round1 세션 172개)도 읽을 수 있지만, 말 끝 전에 끊긴 문항은 앞부분만 남아(세션당 턴 1개) AG-T15b의 문제가 섞인다. 숫자 자릿수 오류 문항은 final_full 14건, 턴 로그 12건으로 비슷하다.
- 명령: `uv run python -m eval.llm_eval --stt-text runs/stt_eval/final_full/rows.jsonl [--judge] --out runs/X`

## 2. 후보

| 후보 | 되묻기 정책 | 응답 내용 |
|---|---|---|
| BASE | 현재 커밋(HEAD). 프롬프트: 자릿수가 틀리면 호출하지 말고 되묻기. 응답기: 자릿수가 틀린 번호는 막고 "한 자리씩" 안내 | 2~3문장, ok는 "상태·날짜·금액만" |
| A | **조회 우선 + 교정**: 프롬프트는 자릿수가 틀려도 스스로 되묻지 말고 들은 번호 그대로 호출, 결과가 invalid_arguments/not_found일 때만 되묻기. 처음 묻기는 "한 자리씩" 없이 평이하게, 필요한 다른 정보(새 주소 등)도 함께. 응답기: 자릿수가 틀린 주문번호는 그대로 보내지 않되, 발신 고객 전화번호가 있으면 get_order_list로 고객 주문을 받아 부분 일치하는 주문이 하나뿐이면 그 번호로 바꿔 호출. 막힌 호출 안내에 "번호 없이 답할 수 있는 정책 안내를 먼저, 주문번호는 열 자리라고 알리고 되묻기" | BASE와 같음(`DIRECTON_PROMPT_DETAIL=0`) |
| B | A와 같음 | **보강**: 함수 결과·정책 안내는 3~4문장까지, ok 결과의 상태·날짜(월·일)·금액·결제 수단·위치를 빠뜨리지 않고 처리 결과에는 매뉴얼의 다음 절차(환불 수단·기간, 회수 방문, 배송비 부담 등)를 한 문장, "내일"만 말하지 말고 월·일 함께, 정책 질문엔 관련 조건 한 가지, 범위 밖이면 도울 수 있는 일 제안, 인계·콜백 사과에 고객 문제와 이유 |
| C(채택) | B + 숫자가 아닌 번호 인자 처리(아래 4절, 1차 결과를 보고 추가) | B와 같음 |

검토 후 버린 안: **틀린 번호를 Mock에 그대로 보내기(단순 조합 방식)**. 기대 호출이 있는 문항은 틀린 번호로 부르든(여분 1 + 누락 1 → 0점) 안 부르든(누락 → 0점) 함수 점수가 같고, 응답도 not_found 뒤에 결국 되묻는다. 반면 일부러 번호를 덜 말한 need_info 문항(기대 [])에서는 여분 호출로 100 → 0이 된다. 기존 단언(`tests/test_responder.py::test_wrong_length_number_not_sent_to_tool`)과도 충돌한다. 그래서 "막되, 고객 정보로 교정할 수 있으면 교정"으로 정했다.

### 부분 일치 규칙과 함수 채점
- `eval/score.py` `tool_match`: 점수 = 일치 수 / (기대 수 + 기대 밖 호출 수). 그래서 교정용으로 get_order_list를 더 부르면 여분 1건이 된다. 기대 호출 1개 문항이면 **0점(되묻기) → 50점(목록 + 교정 호출)** 이 된다. 응대는 고객이 원한 정보를 바로 안내하므로 0 → 대개 만점이다. 손해가 없어 채택했다. LLM이 같은 턴에 이미 get_order_list를 불렀으면 그 결과를 다시 쓴다(추가 호출 없음).
- 규칙(`agent/responder.py` `match_order_id`): 들은 번호(6자리 이상, 자릿수가 틀린 것)와 주문번호의 공통 부분열(LCS)이 7자리 이상, 들은 숫자 중 빠지는 것이 2개 이하, 2등 주문보다 2자리 이상 길 때만 바꾼다. 테스트셋에서 caller가 있고 STT가 자릿수를 틀린 5건 중 3건(T0067 `26140498`, T0108 `61809562`, T0114 `261106027`)이 교정 대상이다. 나머지 T0087(공통 6자리)·T0061(STT가 10자리로 틀림 → 자릿수 검사 대상 아님)은 그대로 둔다. 회원당 주문이 2~3개라 2등과의 차이 조건이 잘 걸린다.
- 전화번호 인자가 자릿수가 틀렸지만 발신 고객 번호와 거의 같으면(같은 LCS 규칙) 고객 번호를 쓴다.
- 발신 고객 번호는 시스템 프롬프트의 "발신 고객 정보 … 전화번호", 없으면 이전 대화 요약의 "이전 대화에서 나온 번호: 전화번호"에서 읽는다. session.py가 Responder에 caller를 넘기지 않아서 이렇게 했다(session.py는 다른 Task 작업 중).

해석:
- **응대 상승은 대부분 내용 보강(B)에서 나온다**(+6.4). 되묻기 정책만 바꾼 A는 +0.7이다. 숫자 문항(digits)에서는 A·B 모두 +8~10이다. 교정된 문항이 안내 내용을 채우고, 막힌 문항도 "열 자리" 안내와 정책 안내를 함께 하기 때문이다.
- 되묻기 수는 크게 줄지 않았다(20 → 19). STT가 틀린 번호는 caller가 없으면 교정할 방법이 없어 여전히 되묻는다. 줄어든 것은 "처음 묻기에 '한 자리씩'을 붙이는" 경우다.

- **게이트웨이 경유 gpt-5.4-mini는 전화번호 인자를 `"[PHONE]"`으로 넣는다**(BASE 포함: T0084, T0147, T0153, T0167). 게이트웨이가 요청의 전화번호를 가리는 것으로 보인다. Gemini 직접 호출에서는 같은 문항이 정상이다(T0084). → 4절.

## 4. 1차 결과를 보고 추가한 응답기 처리 (C)

| 처리 | 동작 |
|---|---|
| 숫자가 아닌 번호 인자 채우기 | 길이 규칙("N자리")이 있는 번호 인자가 숫자가 아니면(`"[PHONE]"`, `"unknown"`, 빈 값, 문장) 이번 고객 발화에서 뽑은 그 길이의 번호를 쓰고, 없으면(전화번호일 때) 확인된 고객 번호를 쓴다. 응답기는 가려지지 않은 원문을 갖고 있어 게이트웨이 마스킹을 되돌린다 |
| 못 채우면 호출 안 함 | 필수 번호 인자를 채우지 못하면 Mock에 보내지 않고 `invalid_arguments`("번호를 받지 못했다, 처음 묻는 것이니 '휴대폰 번호를 말씀해 주시겠어요?'처럼 짧게, 필요한 정보 함께")를 LLM에 돌려준다 |
| 프롬프트 예시 번호 | 고객이 말하지 않았고 고객 번호도 아닌데 인자가 프롬프트 예시 전화번호(01012345678)면 지어낸 번호로 보고 위와 같이 처리한다 |
| 번호 추출 보강 | `utterance_numbers`에 어미 "이야" 추가("010-3457-81이야"). 2차 비교에서 LLM이 덜 들린 9자리 번호에 숫자 2개를 지어 붙여 11자리로 호출한 것(T0133)을 발견했다. 발화 번호를 뽑을 수 있게 되자 기존 번호 교정이 9자리로 되돌리고, 자릿수 검사가 막는다(수정 뒤 T0133 통과 확인: `runs/llm_eval_r2_smoke_pad`) |

## 5. 2차 비교: BASE vs C (STT 텍스트 + 정답 텍스트, 각 172문항)

## 6. 채택

**C를 채택해 반영했다**(기본값). 근거:
- 응대(judge, STT 모드, 50% 배점): BASE 58.9 → B 65.3(+6.4, 같은 시간대 짝 비교 146문항). C의 추가분은 함수 호출만 바꾸므로 응대 내용은 B와 같다.
- 함수(20%): 변동 범위 안에서 같다. 교정 3문항은 0 → 50이고, 1차에서 생긴 need_info 여분 호출은 4절 처리로 막았다. 게이트웨이 `"[PHONE]"` 마스킹으로 전화번호 함수가 0점이 되던 문제도 응답기에서 되돌린다.
- 속도(30%): 첫 소리는 캐시 첫 마디라 영향이 없다. 응답은 평균 약 10자(약 0.3문장) 늘어 TTS 시간·turn.end가 조금 늘 뿐이다. 300자 상한은 유지했고 최대 145자였다.
- 추정 총점 영향(대략): 응대 +6 × 0.5 ≈ **+3점**.

끄는 법(롤백 노브, config.py 대신 환경변수):
- `DIRECTON_PROMPT_DETAIL=0`: 응답 내용 보강을 끈다(후보 A의 프롬프트).
- `DIRECTON_REPAIR_ORDER_ID=0`: 고객 주문 목록 교정을 끈다(숫자가 아닌 인자 처리는 유지).

## 7. 바꾼 파일
- `agent/prompts.py`: 고정부를 `build_fixed(detail)`로 만들었다(`FIXED = build_fixed(detail_enabled())`). 바꾼 규칙은 번호 인자(조회 우선, invalid_arguments/not_found일 때만 되묻기), 처음 묻기(평이하게, 새 주소 등 함께), not_found·invalid_arguments 안내(찾을 수 없다고 말하기, 정책 함께), 보강 규칙(3~4문장, 핵심 필드·다음 절차, 월·일 날짜, 정책 부연, 범위 밖 대안, 인계 사과)이다. 테스트셋 문장은 넣지 않았다(테스트로 확인).
- `agent/responder.py`: `caller_phone_from_system`, `lcs_len`, `match_order_id`, `Responder._repair`(고객 주문 목록 교정, 고객 번호 교정, 숫자가 아닌 번호 인자 채우기·버리기)를 넣었다. 같은 턴의 get_order_list 결과는 다시 쓴다. `_length_error`는 필수 번호 인자 누락을 막고, 안내 문구에 정책 안내와 "열 자리/열한 자리"를 넣었다. `utterance_numbers`에 어미 "이야"를 추가했다.
- `eval/llm_eval.py`: `--stt-text`, `--stt-sessions`, `load_stt_texts`, `run_session_ids`, `is_reprompt`, 행 `input_utterance`·`stt_missing`·`reprompt`, 요약·비교표 `reprompts`.
- `tests/test_reprompt_policy.py`(새 파일, 35개).

## 8. 남은 문제
- **caller가 없는 STT 숫자 오인식은 여전히 되묻기뿐이다**(STT 모드 되묻기 11~19건). 교정 근거가 없다. 남은 수단은 STT 개선(Soniox 비교), 말 끝 전 끊김 감소(AG-T15b)다.
- 교정은 자릿수가 틀린 번호만 다룬다. STT가 10자리로 잘못 들은 번호(T0061 `2615054111`)는 not_found 뒤 되묻는다. caller가 있을 때 not_found 결과를 보고 부분 일치로 다시 부르는 확장은 가능하지만, 틀린 호출이 여분으로 남아(1/3점) 이번에는 넣지 않았다.
- 응대 비교는 judge 1회씩이고 게이트웨이 gpt-5.4-mini + 3.1-flash-lite 혼합 조건이다. gemini-3.5-flash-lite 단독으로 judge를 다시 재지 못했다. 통합 측정(AG-T15d)에서 확인이 필요하다.
- 응답이 조금 길어지면서 같은 안내를 두 번 하는 응답이 드물게 보인다(예: "열 자리인데 한 번 더 말씀해 주시겠어요? 번호를 한 자리씩 … 다시 말씀해 주시…").
