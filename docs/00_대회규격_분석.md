## 1. 초안과 실제 환경의 차이 (가장 중요)

| 항목 | 초안(아이디어 Draft.md) | Starter Kit 기준 실제 환경 | 계획 반영 |

## 2. WebSocket 프로토콜 (측정기 ↔ 우리 서버)

1. 측정기가 접속 후 텍스트 JSON `session.start`를 보낸다.
   ```json
   {"type":"session.start","session_id":"DEMO-1-abc","case_id":"DEMO1","now":"2026-11-21 11:00",
    "history":[],"caller":null,"tools_url":"http://localhost:8100",
    "audio":{"encoding":"pcm_s16le","sample_rate":16000,"channels":1}}
   ```
   - `caller`: 고객 프로필(name, phone, email) 또는 null
   - `history`: 이전 대화 (형식 미정, 데모는 빈 배열)
   - `tools_url`: 함수 호출 대상 Mock API 주소
2. 이후 20ms 단위 PCM 바이너리가 **실시간 속도로** 계속 온다. 고객 발화가 끝나도 **무음 프레임이 계속 온다**(말 끝 탐지는 우리 몫).
3. 우리는 같은 형식(16kHz s16le mono)의 PCM 바이너리로 응답 음성을 보낸다.
   - 선택: `{"type":"agent.transcript","text":"..."}` 텍스트 이벤트 (측정기가 `agent_text`로 수집 → 응대 채점에 쓰일 가능성 높음)
4. 응답을 마치면 `{"type":"turn.end"}`를 반드시 보낸다. 측정기는 이걸 받으면 세션을 끝낸다.
5. 측정기는 말 끝 이후 25초(`TAIL_TIMEOUT`)가 지나면 강제 종료한다.

## 3. 속도 채점 방식 (score_demo.py 기준, 연습용)

- `first_sound` = (우리 음성 프레임 중 **RMS ≥ 300인 첫 프레임의 도착 시각**) − (실제 말 끝 시각 `speech_end`)
  - `speech_end`는 음성 파일 메타(`meta.json`)의 정답값이다. 우리의 판정과 무관하다.
  - 도착 시각 기준이므로 음성을 실시간보다 빨리 몰아서 보내도 된다. **첫 덩어리를 최대한 빨리 보내는 것**이 핵심이다.

| first_sound | 점수 |
| --- | --- |
| ≤ 1.5초 | 100 |
| ≤ 2.0초 | 90 |
| ≤ 2.5초 | 80 |
| ≤ 3.0초 | 70 |
| ≤ 3.5초 | 60 |
| ≤ 4.0초 | 50 |
| ≤ 5.0초 | 30 |
| ≤ 6.0초 | 10 |
| 초과 | 0 |

- **0점 처리 조건**: `spoke_before_end`(말 끝 전에 유성음 도착), 에러, `turn.end` 없음, `turn.end`가 말 끝 후 25초 초과
- `after_tool_sound`: 마지막 함수 응답 시각 → 그 이후 첫 유성음까지 걸린 시간도 기록된다(공식 채점 반영 여부 미정).

### 시사점

1. **구간이 0.5초 단위로 거칠다.** 1.5초 안이면 100점이므로, 초안의 "턴 종료 확률 0.8↑이면 100ms 대기" 같은 공격적 단축은 점수 이득이 거의 없다. 반면 말을 일찍 끊으면 그 문항 속도가 0점이고, 부분 발화로 답하게 되어 응대·함수 점수도 같이 잃는다.
   → **엔드포인팅의 목표를 "최소 대기"에서 "1.5초 예산 안에서 잘못 끊기 0에 가깝게"로 바꾼다.**
2. **첫 유성음만 빨리 나가면 된다.** 캐시해 둔 짧은 첫 마디("네, 고객님." / 케이스별 첫 문장)를 판정 즉시 보내고, 본 응답(LLM+TTS)은 그 뒤에 이어 붙인다. 초안의 "확인 문구 사전 합성 캐싱"이 바로 이 역할을 맡는다.
3. 예산 분해 (목표 1.5초 이하, 여유 0.2초):
   - 말 끝 → 우리 침묵 감지 시작: 0~60ms (프레임 단위, VAD 지연)
   - 엔드포인팅 대기: **기본 500~800ms**, 상황별 조정
   - 첫 마디 결정 + 캐시 PCM 송신: ~50ms
   - 네트워크(로컬 실행이면 ≈0)
   → 대기를 최대 ~1.1초까지 써도 100점 구간이다.
4. 첫 마디 뒤 본 응답까지의 공백은 속도 점수에는 안 잡히지만 응대 품질(자연스러움) 평가에 영향을 줄 수 있다. 공백이 길면 필러("잠시만요, 확인해 볼게요")를 넣는다.

## 4. 함수(Mock API) 규격

- `GET /tools` → `[{"type":"function","function":{name, description, parameters}}]` (OpenAI 툴 형식 그대로)
- `POST /tools/{name}` + JSON 인자 + **`X-Session-Id` 헤더 필수** (빠지면 호출하지 않은 것으로 채점)
- `GET /calls?session_id=` → 호출 기록 `{session_id, name, arguments, matched, t_response}`
- `matched` = 미리 정의된 입력과 일치했는지. **함수 점수는 함수 이름과 인자의 정확한 일치로 매길 가능성이 크다.**
  - 예: 주문번호 "데모 일 영영 일" → `"DEMO1001"`로 정규화해야 matched
  - 전화번호는 `"01000001234"`처럼 하이픈 없는 형식
- 데모 함수: `get_order_info(order_id)`, `request_callback(phone_number)`
- 공식 함수 14개, 공통 데이터, 평가 서버 사용 방식은 **미확정**.

### 시사점

- 인자 정규화(한국어 숫자 읽기 → 숫자, 영문 철자 읽기 → 대문자, 전화번호 포맷)가 함수 점수를 좌우한다. STT 후처리 + LLM 프롬프트 + 코드 검증을 겹쳐 둔다.
- `caller.phone`이 있으면 고객에게 번호를 다시 묻지 말고 그대로 쓴다(DEMO3 사례).
- 함수 응답 뒤 첫 소리까지(`after_tool_sound`)도 측정되므로, 함수 결과를 받으면 바로 문장 단위 TTS로 넘긴다.

## 5. 측정기 동작 특성

- 기본 동시성 4 → 서버는 세션 4개 이상을 동시에 처리해야 한다. 외부 API 동시 연결 수·분당 호출 한도를 확인해야 한다.
- 395문항 × (STT + 판정 + LLM + TTS) 호출량을 기준으로 비용·한도를 계산해야 한다.
- 이미 끝난 문항은 다시 측정하지 않으므로, 재측정할 때는 새 `--out` 폴더를 쓴다.
- 데모 음성 3개는 영어 합성음이다. **한국어 테스트 음성은 우리가 만들어야 한다.**
