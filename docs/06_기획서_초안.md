## 1. 문제 정의

전화 고객센터는 고객이 말을 마치고 답이 나올 때까지의 침묵이 길면 바로 불만이 된다. 반대로 고객이 잠깐 숨을 고르거나 주문번호를 끊어 읽는 사이에 상담원이 끼어들면 더 나쁘다. 한국어 음성 AI 상담원을 만들 때 부딪히는 문제는 세 가지다.

1. **말 끝을 언제 판단할 것인가.** 한국어는 "주문번호가요 … 이육일일 …", "~했는데요 …"처럼 연결어미·조사·숫자 묶음 뒤에서 자주 쉰다. 고정 침묵(예: 800ms)으로 끊으면 말 중간에 끼어들고, 길게 기다리면 느리다. 대회 규칙상 고객 말이 끝나기 전에 소리를 내면 그 문항 속도는 0점이다.
2. **STT → LLM → TTS를 차례로 기다리면 느리다.** 우리 환경에서 실측한 부품 지연을 더하면(STT 확정 0.43초 + LLM 첫 문장 0.8~1.3초 + TTS 첫 바이트 0.47초) 본 응답 첫 소리까지 p50 1.7~2.2초다(`bench_providers.md`). 단순 조합을 그대로 돌리면 첫 소리 p50이 5.16초였다(`naive_benchmark.md`).
3. **음성으로 들은 숫자·이름을 업무 함수에 정확히 넣어야 한다.** "공일공 일이삼사…", "엑스라지", "회색"처럼 말한 값을 함수 인자(`01012345678`, `XL`, `그레이`)로 바꿔야 하고, 전화 채널에서는 STT 숫자 정확도가 63~68%까지 떨어진다(`stt_tuning.md`).

대회 도메인은 **건강기능식품 쇼핑몰 CS**이며 업무는 배송, 주문 취소, 반품·환불, 교환, 결제, 상품 문의, 상담원 연결의 7종이다. 공식 매뉴얼·함수·데이터는 당일 09:00에 공개되므로, 사전 개발은 가상 쇼핑몰 데이터로 하고 당일 교체할 수 있게 만드는 것이 전제다.

## 2. 핵심 사용자

| 사용자 | 상황 | 바라는 것 |
|---|---|---|
| 전화 고객 | 배송 조회·취소·반품 등을 전화로 처리하려는 사람. 통화 잡음, 작은 목소리, 숫자 끊어 읽기, 말 중간 정정이 흔하다 | 끼어들지 않고, 빨리, 정확히, 짧게 답해 주는 것. 해결이 안 되면 사람에게 바로 연결 |
| 쇼핑몰 운영자 | 반복 문의를 자동화하려는 CS 책임자 | 매뉴얼에 없는 말을 하지 않는 것, 사람이 필요한 문의는 정확히 넘기는 것, 매뉴얼·데이터만 바꿔 운영할 수 있는 것 |
| 사람 상담원 | 인계받는 쪽 | 인계 사유가 한 줄로 정리되어 넘어오는 것 |

## 3. 주요 기능

1. **실시간 말 끝 판단**: 침묵 길이 + 인식된 문장 끝 모양(텍스트 종류) + 누적 발화 길이로 대기 시간을 정하는 보정된 턴 결정기.
2. **미리 준비하는 응답**: 고객이 200ms 멈추면 LLM 호출을 먼저 시작하고 첫 문장 음성까지 미리 합성해 둔다(송신은 하지 않는다). 말 끝이 확정되면 최종 텍스트와 같은지 비교해 재사용한다.
3. **즉시 첫 소리**: 말 끝 확정 후 약 10ms 안에 첫 소리를 보낸다(캐시 첫 마디 또는 선합성된 첫 문장).
4. **업무 처리(함수 호출)**: 14개 업무 함수(주문 조회·배송 추적·취소·반품·교환·주소 변경·환불 조회·상품·재고·쿠폰·콜백·상담원 연결 등)를 `X-Session-Id` 헤더와 함께 호출한다.
5. **한국어 인자 정규화**: 한국어 숫자 읽기("공일공/영일영"), 영문 철자 읽기, 날짜("내일", "다음 주 월요일"), 상품명·옵션 별칭(엑스라지↔XL, 회색↔그레이, 부분 상품명), 주문번호 자릿수 검사와 고객 주문 목록 기반 교정.
6. **Human Handoff**: 9절 기준에 해당하면 말로만 안내하지 않고 `transfer_to_agent`를 실제로 호출한다(영업시간 외에는 콜백 접수).
7. **당일 교체**: 매뉴얼·브랜드·말투 파일, Mock 데이터·함수 정의 파일을 바꾸면 프롬프트·정규화 규칙(번호 자릿수 등)이 따라 바뀌게 한다(AG-T17, 〔당일 확인〕).

## 4. 사용자 흐름

```
고객: "주문번호가요 … 이육일일 일오공 이삼일이요. 언제 와요?"
  │  (숫자 묶음 사이 쉼 → 결정기가 '숫자 미완'으로 보고 더 기다림)
  │  말 끝 + 200ms : STT 부분 결과로 LLM 선호출 시작, 첫 문장 음성 선합성(버퍼에만)
  │  말 끝 확정(대기 0.7~2초, 텍스트 종류별) : STT 최종 텍스트와 선호출 입력 비교
  ▼
상담원: [~10ms] 첫 소리 → 함수 track_delivery("2611150231") → "11월 21일 도착 예정입니다 …"
  │  agent.transcript(전체 응답 텍스트) → turn.end
  ▼
(인계 조건이면) "불편을 드려 죄송합니다. 담당 상담원에게 바로 연결해 드릴게요." + transfer_to_agent(reason)
```

- 정보가 부족하면(번호 없음 등) 함수를 부르지 않고 필요한 정보만 짧게 묻는다("필요한 정보를 받기 전에 업무 실행 금지").
- 고객 발화 중 상담원 발화 중단(바지인)·추가 질문 대응은 개발 중이다(AG-T19, 〔당일 작성〕).

## 5. 기술 스택

| 구간 | 선택 | 이유(실측) |
|---|---|---|
| 서버 | Python 3.12, asyncio, websockets | 측정기 WebSocket 프로토콜 직접 구현, 동시 4세션 |
| STT | `gemini-3.5-transcribe-live`(스트리밍) | finalize → 최종 텍스트 p50 0.40초(172문항). 일괄 STT는 2.2~10.9초 + 503 잦음 → 제외 |
| VAD | Silero VAD(ONNX, 로컬 CPU) | 프레임당 0.1~0.2ms |
| 턴 결정기 | 자체 보정 표(텍스트 종류 × 발화 길이 → 대기) | Smart Turn은 한국어 통화 음성에서 변별력 없음(AUC 0.57) → 제외 |
| LLM | `gemini-3.5-flash-lite` + 500ms 뒤 `gemini-3.1-flash-lite` 동시 요청(hedge) + 컨텍스트 캐시 | 첫 이벤트 p95 3.73 → 1.64초, 호출당 비용 0.248 → 0.074¢ |
| TTS | edge-tts `ko-KR-SunHiNeural`(16kHz 변환, 레벨 정규화), 장애 시 대체 TTS | 첫 바이트 p50 0.47초. edge-tts는 비공식 서비스라 대체 경로 준비(AG-T18, 〔당일 확인〕) |
| Mock API | 표준 라이브러리 HTTP 서버, 함수 14개, `--data/--tools` 파일 교체 | Starter Kit 템플릿과 같은 경로·형식 |
| 평가 | 자체 측정기(Starter Kit 확장)·채점기·오프라인 LLM 평가기·턴 시뮬레이터 | 모든 결정을 수치로 비교 |

모든 외부 서비스는 인터페이스(`agent/core/types.py`) 뒤에 있어 환경변수로 교체할 수 있다. Soniox STT·OpenAI LLM·Gemini TTS 어댑터도 구현돼 있다.

## 6. 시스템 아키텍처

```
측정기 ─WS─▶ 세션(동시 다수) ─┬─ STT  gemini-3.5-transcribe-live (부분 결과 숫자 복원)
                              ├─ VAD  Silero → 턴 결정기 (텍스트 13묶음 × 발화 길이 4구간 → 대기, 상한 1.3초 / 미완 표현 최대 2초)
                              ├─ 선호출  침묵 200ms → LLM 시작 + 첫 문장 선합성(버퍼)
                              ├─ 첫 소리  확정 즉시 선합성 문장 또는 캐시 첫 마디
                              ├─ 응답기  LLM(hedge + 캐시) ⇄ 함수 호출 루프, 문장 단위 TTS
                              │     └ 정규화: 숫자·철자·날짜·상품명/옵션·번호 교정·자릿수 검사·인계 안전망
                              ├─ 함수  tools_url(측정기 중계) + X-Session-Id
                              └─ TTS  edge-tts(→ 대체) → 16kHz PCM + agent.transcript + turn.end
```

불변 규칙: 고객 말 끝 확정 전에는 어떤 오디오도 보내지 않는다(테스트로 보장). PCM은 항상 16kHz s16le mono이고, 다른 샘플레이트는 경계에서 변환한다.

## 8. AI 처리 범위

| AI가 처리 | 규칙(코드)이 처리 | 사람에게 넘김 |
|---|---|---|
| 의도 파악, 매뉴얼 기반 안내, 함수 선택, 응답 문장 생성 | 말 끝 판단, 첫 소리 타이밍, 숫자·날짜·상품명 정규화, 번호 자릿수 검사·교정, 말로 연결을 약속하고 함수를 안 부른 경우 자동 호출(안전망), 응답 300자 상한 | 9절 기준 |

원칙: 함수 결과와 매뉴얼에 없는 정보는 안내하지 않는다. 확인되지 않은 정책을 지어내지 않고, 모르면 콜백·인계를 제안한다.

## 9. Human Handoff 기준

다음 중 하나면 `transfer_to_agent`를 **함수로** 호출한다(말로만 안내 금지). 상담원 연결 시간(평일 09~18시, 점심 12~13시 제외) 밖이면 `request_callback`으로 콜백을 접수한다. 인계 전에 한 문장으로 사과·공감하고, 사유(`reason`)를 한 줄로 남긴다.

| # | 기준 | 예 | 이유 |
|---|---|---|---|
| 1 | **섭취 후 몸 불편·건강 이상·의료 판단 질문** | "이거 먹고 두드러기가 났어요", "약이랑 같이 먹어도 돼요?" | 건강기능식품은 의학적 판단이 필요하고, 잘못 안내하면 위험하다. 공식 예시와 일치. 사고·부상 언급은 이미 인계 규칙에 있으며, 섭취 후 이상은 당일 공식 매뉴얼로 문구를 확정한다(AG-T22, 〔당일 확인〕) |
| 2 | 고객의 **직접 요청** | "사람이랑 통화할래요", "상담원 바꿔 주세요" | 요청 무시가 가장 큰 불만 요인 |
| 3 | **욕설·강한 불만** | 같은 불만 반복, 격앙된 표현, 소비자원 신고 언급 | 자동 응답이 감정을 키울 수 있다 |
| 4 | **반복 실패** | 같은 요청을 세 번 이상 이해하지 못함 | 무한 반복 방지 |
| 5 | **법적 문제** | 소송, 개인정보 유출, 사고·부상 | 책임 판단이 필요 |
| 6 | **매뉴얼·함수로 처리할 수 없는 예외** | 반품 기한 지난 불량, 결제 금액 오류, 대량 주문 | 정책 밖 판단 금지 |

실측: 프롬프트 규칙 + "말로 연결 약속 시 자동 호출" 안전망으로 오프라인 불만·인계 범주 함수 일치가 0.12 → 0.88이 되었다(`llm_tuning.md`). 실서버(round1)에서는 0.53이었고, 차이의 주원인은 말 끝 전 응답(6건)이었다(`round1.md`).

## 10. 주요 기술적 의사결정

### 10.1 평가 방법

| 도구 | 내용 |
|---|---|
| 평가용 테스트셋 172문항 | 범주 7종(조회 39, 실행 34, 후속 30, FAQ 19, 정보 부족 19, 불만·인계 17, 범위 밖 14), 함정 태그(발화 중 쉼 34, 숫자 54, 간투사 16, 자기 정정 8 등). 화자 11종(상담원 목소리 제외), 통화 조건 증강: 채널 3종(광대역/전화 대역/μ-law), 잡음 5종(white·pink·babble·hum 등), SNR 4단계, 음량 3단계, 패킷 손실, 말 속도 3단계. 모든 기대 함수 호출이 Mock에서 matched 되는지 테스트로 보장 |
| 턴 감지 보정셋 771발화 | 쉼 위치를 알고 합성해 "쉼 = 미완, 마지막 끝 = 완료" 라벨 자동 생성. 화자·문장 비중복 train 618 / test 153. 2차 보정에서 블록 2·3을 더해 test 228 |
| 측정·채점 | Starter Kit 측정기 확장(동시 4), 속도 표는 Starter Kit과 동일, 함수는 이름 + 키 인자 일치, 응대는 LLM judge(`gemini-3.8-flash`) |
| 오프라인 평가기 | 오디오 없이 정답 텍스트 또는 실제 STT 텍스트로 실제 프롬프트·응답기 루프를 돌려 프롬프트 변경을 빠르게 비교 |
| 기준선 | 흔한 최소 구현(고정 침묵 800ms + STT + LLM + 전체 문장 TTS, 같은 모델)을 같은 172문항·측정기·채점기로 측정 |

한계: 테스트 음성은 모두 합성음이고, 도메인은 가상 쇼핑몰(의류·전자)이다. judge는 텍스트만 보므로 공백·반복 채움말을 감점하지 않는다.

### 10.2 결정과 근거

| 결정 | 버린 안 | 근거(실측) |
|---|---|---|
| 말 끝 판단을 "최소 대기"가 아니라 **"1.5초 예산 안에서 잘못 끊기 최소"**로 | 공격적 단축(확률 높으면 100ms) | 속도는 1.5초 이내면 만점, 말 끝 전 소리는 0점. 첫 소리가 확정 후 ~10ms라 대기를 1초 넘게 써도 만점 구간 |
| **텍스트 종류 × 발화 길이 보정 표** | Smart Turn v3, 고정 침묵 | Smart Turn AUC 0.57(함정 쉼에서 p 0.97 > 진짜 끝 0.88), 텍스트 규칙 0.83, 텍스트+발화 길이 0.894. 1차 보정: 보정셋 test 잘못 끊기 42.5 → 15.7%(1.1초 이하 쉼 22.9 → 1.3%). 2차 보정: 보정셋 test 19.7 → 10.1%, 172문항 시뮬레이션 말 끝 전 확정 28 → 13(교차 검증 18), 진짜 말 끝 지연 p95 1292ms |
| **침묵 200ms 선호출 + 첫 문장 선합성** | 확정 후 LLM 시작 | 선호출 재사용 2/20 → 24/30, 선합성 재사용 14/30(`session_tuning.md`) |
| **LLM hedge 500ms + 컨텍스트 캐시** | 2.5초 폴백, 두 모델 동시(race) | 첫 이벤트 p95 3.73 → 1.64초, 첫 마디 뒤 공백 p90 2231 → 207ms, turn.end p50 5.90 → 3.68초, 비용 약 70% 절감. race는 p95가 0.3초 짧지만 3.1 모델이 절반 가까이 처리(3.1은 툴 대신 되묻는 경향) |
| 번호 되묻기 **조건부 완화 + 고객 주문 목록 교정 + 응답 내용 보강** | 자릿수 틀리면 항상 되묻기 | judge(STT 텍스트, 146문항) 58.9 → 65.3, 함수는 변동 범위 안(84.2 → 83.6) |
| 상품명·옵션 **카탈로그 정규화** | LLM에 맡김 | 상품 관련 21문항 함수 일치 0.71 → 0.79 |
| 잡음 VAD 래퍼 **기본 끔**(AD8) | 켬 | babble 말 끝 놓침 34 → 21%지만 잘못 끊기 16.7 → 18.4%. 잘못 끊기(0점) 손해가 놓침(80~90점)보다 큼 |
| STT 설정 튜닝 대신 **자릿수 검사·교정** | STT 일괄 재인식 | 설정 실험으로 숫자 정확도 74.1% 그대로, 재인식은 1.5~3초 추가에 개선 0~1건 |

### 10.3 속도와 품질의 trade-off

| 축 | 선택 | 대가 |
|---|---|---|
| 대기 시간 vs 끼어들기 | 미완 표현(연결어미·조사·숫자·정정·쉼표 끝)은 최대 2초까지 기다리고, 그 밖은 상한 1.3초 | 진짜 말 끝 지연 p50 677 → 816ms. 1.4초가 넘는 쉼, "완결 문장 + 쉼 + 다음 문장"은 여전히 못 막는다 |
| 첫 소리 vs 자연스러움 | 확정 즉시 첫 소리 | 모든 답을 같은 채움말로 시작하면 UX 감점 사례(공식 안내). 선호출로 답이 준비되면 첫 마디 없이 바로 답하고, 아닐 때만 상황별로 다른 짧은 첫 마디를 쓰도록 재설계 중(AG-T20, 〔당일 측정〕) |
| 정확도 vs 되묻기 | 자릿수가 틀린 번호는 함수에 보내지 않고, 고객 정보로 교정되면 교정, 아니면 짧게 되묻기 | 고객 번호가 없으면 STT 오인식 문항은 되묻기로 남는다 |
| 빠른 모델 vs 안정성 | 3.5-flash-lite 우선, 500ms 뒤 3.1 동시 | 3.1이 답하는 비율 약 16%, 취소된 요청도 과금(캐시 단가라 작음) |
| 응답 길이 | 3~4문장(상태·날짜·금액·다음 절차는 빠뜨리지 않음), 300자 상한 | 평균 약 10자 늘어 turn.end가 조금 늘어남 |
