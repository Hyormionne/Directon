# 13. 사용자 경험 심사기준 (팀 내부 기준)

> 작성일: 2026-11-21. 출처: 팀 회의 녹취(2026-11-21 오전), `directon-2026-voice-cs/SCORING.md`, `README.md`, `data/brand/scenarios.md`·`style.json`·`information.json`.
> 행사 전체 평가는 **사용자 경험 50 / 시스템 점수 20 / 발표 20 / 기획서 10**이다. 사용자 경험은 가장 큰 항목이지만 **세부 기준이 공개되지 않았다.** 이 문서는 심사위원이 직접 전화를 걸어 써 볼 때 무엇을 볼지 추정해 만든 **팀 내부 기준**이다. 실험안을 비교하고, 기획서·발표에서 설계 근거를 설명할 때 이 기준을 쓴다.

## 1. 우리가 정한 "좋은 사용자 경험"

> **고객이 가장 적은 말과 가장 짧은 시간으로 전화한 목적을 이루는 것.**

회의에서 합의한 원칙이다. 친절한 말투는 없으면 감점되지만 있다고 해서 점수가 크게 오르지는 않는다. 점수를 가르는 것은 목적 달성까지 걸리는 단계 수다.

| # | 원칙 | 회의에서 나온 근거 |
|---|---|---|
| P1 | **목적 달성이 먼저다.** 묻는 것에 바로 답하고, 처리할 것은 처리한다 | "내가 원하는 걸 최대한 빠른 시간 안에 받는 것" |
| P2 | **고객이 누구인지 빨리 알아챈다.** 발신번호가 있으면 다시 묻지 않는다 | "이름 말해, 아이디 말해 하면 짜증나잖아요" |
| P3 | **선택지를 주지 않는다.** 넘길 때는 넘기고, 접수할 때는 접수하고, 안 되면 안 된다고 말한다 | "상담원 연결해 드릴까요, 아니면…" 같은 질문은 전화에서 부담이다 |
| P4 | **대화가 끊기지 않는다.** 고객 말을 자르지 않고, 말하기 시작하면 중간에 멈추지 않는다 | 엔드포인팅이 정량 지표에서 가장 큰 문제다. 함수 호출 뒤 LLM을 한 번 더 부르면 공백이 생긴다 |
| P5 | **맥락에 맞게 말한다.** 템플릿 티가 나면 안 된다 | 전화까지 거는 고객은 사람다운 응대를 기대하고, 불만이 생기면 강하게 표현한다 |
| P6 | **위험한 건 바로 사람에게 넘긴다.** 사람을 찾으면 바로 연결한다 | 건강 상태나 복용약 문의는 의료 위험이 있다. 클라이언트(쇼핑몰) 입장에서는 콜 수를 줄여야 하므로 넘기는 것을 남용하지 않는다 |

## 2. 심사 항목과 배점 (100점 환산)

항목마다 0/1/2점으로 매기고 가중치를 곱한다. 한 통화(다중 턴 전체)를 단위로 매긴다.

| 항목 | 가중치 | 무엇을 보나 |
|---|---|---|
| A. 목적 달성 | 30 | 고객이 원한 결과(답변·접수·인계)를 얻었는가, 몇 턴 만에 얻었는가 |
| B. 대화 리듬 | 20 | 말 끊기, 침묵, 채움말, 조회 뒤 공백 |
| C. 본인 확인·번호 처리 | 15 | 필요한 정보만, 한 번에, 틀려도 빨리 바로잡기 |
| D. 맥락 적합성 | 15 | 앞 대화 반영, 결론 먼저, 공감, 사실 정확성 |
| E. 진행 방식 | 10 | 선택지 나열 금지, 한 번에 하나만 묻기, 짧은 문장 |
| F. 안전·인계 판단 | 10 | 의료 위험 문의, 명시적 상담원 요청, 지어내지 않기 |

### A. 목적 달성 (30)

| 점수 | 기준 |
|---|---|
| 2 | 고객이 원한 결과를 얻었고, 불필요한 턴이 없다(질문 → 필요한 정보 1회 → 결과) |
| 1 | 결과는 얻었지만 같은 정보를 두 번 묻거나 불필요한 확인이 1회 이상 있다 |
| 0 | 결과를 얻지 못했다(엉뚱한 답, 처리 누락, 질문 회피, 답 없이 끊김) |

- 접수는 승인 전 단계이므로 "접수됐고 이렇게 진행된다"까지 말하면 달성으로 본다(scenarios.md 6번).
- 인계가 맞는 상황에서 바로 인계했다면 달성으로 본다.

### B. 대화 리듬 (20)

| 점수 | 기준 |
|---|---|
| 2 | 말 끊기 0회. 첫 소리 1.5초 이내. 조회 뒤 답 3.5초 이내. 말하는 도중 멈추는 곳 없음 |
| 1 | 첫 소리 2~3초, 또는 문장 사이 1초 이상 공백이 1회 있음 |
| 0 | 고객 말을 끊음, 3초 이상 침묵, 같은 채움말을 매 턴 반복 |

- 채움말("확인해 보겠습니다")은 상황별로 다르게 쓰고 직전 턴과 겹치지 않게 한다(`docs/decisions/round2.md` 첫 마디 정책).
- 채움말 뒤에 실제 답이 늦으면 오히려 경험이 나빠진다. 채움말은 시간을 버는 수단이고, 답을 대신하지 않는다.

### C. 본인 확인·번호 처리 (15)

| 점수 | 기준 |
|---|---|
| 2 | 발신번호가 있으면 묻지 않고 조회. 없으면 주문번호 또는 전화번호 **하나만** 묻는다. 번호가 애매하면 후보로 되묻는다("끝자리 1152로 주문하신 관절 가드 맞으세요?") |
| 1 | 정보는 얻었지만 2개 이상을 한꺼번에 요구하거나, 번호를 통째로 다시 불러 달라고 한다 |
| 0 | 이미 받은 정보를 다시 묻는다. 틀린 번호로 조회·접수하고 그대로 안내한다 |

- 고객을 알아본 뒤의 고객 ID·전화번호는 LLM이 아니라 프로그램이 함수 호출에 넣는다. 모델이 엉뚱한 번호를 쓰는 실수를 막기 위해서다.
- 건강기능식품은 먹은 뒤 연락하는 경우가 많다. 그래서 최근 주문을 먼저 후보로 두는 것이 합리적이다.

### D. 맥락 적합성 (15)

| 점수 | 기준 |
|---|---|
| 2 | 질문의 핵심에 결론부터 답한다. 앞 대화 내용(이미 말한 사정, 상품명)을 반영한다. 불편에는 짧게 공감한 뒤 안내한다(style.json) |
| 1 | 사실은 맞지만 정해진 문장처럼 들린다. 결론이 뒤에 나온다 |
| 0 | 조회 결과·브랜드 정보와 다른 사실을 말한다. 앞 대화를 무시하고 처음부터 다시 묻는다 |

- 예: "배송 언제 와요?"에는 "내일 도착 예정이에요"를 먼저 말하고 사정 설명은 뒤로 미룬다.
- 예: "효과가 없어서 반품하고 싶다"는 그냥 반품을 접수하는 상황일 수도, 섭취 기간을 안내할 상황(information.json "제품효과에대한안내": 2주 이상 섭취)일 수도 있다. 고객 말에서 의도가 분명하면 그대로 처리하고, 섭취 안내는 한 문장으로 덧붙이는 정도만 한다.

### E. 진행 방식 (10)

| 점수 | 기준 |
|---|---|
| 2 | 선택지를 나열하지 않는다. 한 턴에 질문은 최대 하나다. 문장이 짧다(한 턴 2~3문장) |
| 1 | 질문 2개를 한 턴에 묻거나, 한 턴이 4문장 이상이다 |
| 0 | ARS식 선택지("1번… 2번…", "A 할까요 B 할까요")를 준다. 고객이 기억해야 할 정보를 길게 나열한다 |

### F. 안전·인계 판단 (10)

| 점수 | 기준 |
|---|---|
| 2 | 건강 상태·복용약·부작용 문의는 단정하지 않고 바로 인계한다. "상담원 연결해 주세요"에는 즉시 연결(전화번호·운영시간 안내)한다. 모르는 것은 지어내지 않는다 |
| 1 | 인계는 했지만 그 전에 불필요한 질문을 1회 이상 했다 |
| 0 | 의료 판단을 단정해서 답한다. 근거 없는 정책을 지어낸다. 처리할 수 있는 문의를 습관적으로 넘긴다 |

## 3. 즉시 0점 사례 (어느 항목이든 하나라도 나오면 그 통화는 최대 40점)

1. 고객이 말하는 도중에 상담원 음성이 나간다(속도 0점 조건과 같다)
2. 브랜드 정보·조회 결과에 없는 가격·정책·배송일을 말한다
3. 고객이 요청하지 않은 접수(취소·반품·교환·콜백)를 한다
4. 건강·복용 문의에 "드셔도 괜찮습니다"처럼 단정한다
5. 3초 이상 아무 소리가 없다
6. 같은 채움말을 매 턴 똑같이 반복한다

## 4. 트레이드오프와 판단 규칙

| 충돌 | 규칙 |
|---|---|
| 본인 확인을 철저히 vs 질문 수를 줄이기 | 발신번호 → 바로 조회. 없으면 번호 하나만 묻는다. 이름·ID를 처음부터 묻지 않는다 |
| 템플릿(빠름) vs LLM 생성(자연스러움) | LLM을 쓴다. 대신 **호출을 한 번으로 끝낸다.** 함수 명세와 가능한 결과값(배송중·배송완료·입금전 등)을 미리 주고 결과별 답을 함께 만들어 두면, 조회 결과가 오자마자 값만 넣어 내보낸다. 함수 결과를 받고 LLM을 다시 부르지 않는다 |
| 빠른 시작 vs 말 끝까지 듣기 | 끝나기 2~3단어 전쯤 미리 생성을 시작한다. 말이 끝나면 판단 모델로 "의미가 바뀌었나"를 확인해, 안 바뀌었으면 만들어 둔 답을 쓰고 바뀌었으면 다시 생성한다 |
| 컨텍스트 많이 vs 지연 | 한 통화 분량은 다 넣어도 된다(GPT-5.4 mini 컨텍스트 여유 충분). 시나리오·브랜드 정보는 분류기로 해당 부분만 넣는 안과 전부 넣는 안을 실험해서 정한다 |
| 고객 만족(바로 사람 연결) vs 클라이언트 이익(콜 감소) | 명시적 요청과 의료 위험 문의만 즉시 인계한다. "잘 모르겠다"는 이유로는 넘기지 않는다 |
| 음성 품질(TTS) | 지정 모델(Gemini 3.8 Flash-Lite TTS) 안에서 프롬프트로 말투만 다듬는다. 투자 우선순위는 낮다. 기계음 티가 크게 나면 감점 요인이다 |

## 5. 측정 방법

### 5.1 정량 지표 (자동)

| 지표 | 정의 | 목표 |
|---|---|---|
| 목적 달성 턴 수 | 첫 발화부터 결과(답·접수·인계)까지 상담원 턴 수 | 평균 2턴 이하 |
| 고객 발화량 | 목적 달성까지 고객이 말한 글자 수 합 | 낮을수록 좋음 |
| 재질문 수 | 이미 받은 정보를 다시 물은 횟수 | 0 |
| 말 끊기 | 고객 말 도중 상담원 음성 발생 | 0 |
| 첫 소리 / 조회 뒤 답 | SCORING.md 정의 그대로 | ≤1.5초 / ≤3.5초 |
| 채움말 반복 | 연속 두 턴 같은 첫 마디 | 0 |
| 인계 정확도 | 인계가 정답인 문항에서 인계했는가, 아닌 문항에서 안 했는가 | 둘 다 100% |

### 5.2 LLM 판정 (반자동)

측정기 문항은 한 턴 단위다(이전 대화는 `history`로 고정). 그래서 LLM 판정은 **history + 마지막 고객 발화 → 우리 응답**을 2장의 A~F 기준으로 매긴다. 다중 턴의 흐름(A의 턴 수, C의 재질문)은 5.3 사람 테스트로 보완한다.

판정 프롬프트 초안:

```
너는 전화 상담 품질 심사위원이다. 아래 기준으로 상담원의 마지막 응답을 평가한다.
[기준] A 목적 달성 / B 리듬(채움말 반복·장황함) / C 본인 확인(재질문·다중 요구)
       / D 맥락(결론 먼저·사실 일치·공감) / E 진행(선택지 나열·질문 2개 이상) / F 안전·인계
각 항목 0/1/2와 근거 한 줄. 즉시 0점 사례(지어낸 사실, 요청 없는 접수, 의료 단정)가 있으면 표시.
[시나리오] {scenarios.md 해당 부분}  [브랜드 정보] {관련 항목}  [조회 결과] {tool 결과}
[대화] {history}  [고객] {마지막 발화}  [상담원] {응답}
JSON으로 출력: {"A":..,"B":..,"C":..,"D":..,"E":..,"F":..,"fatal":[..],"note":".."}
```

### 5.3 사람 직접 통화 (정성)

UX 담당 3명이 페르소나를 나눠 같은 시나리오를 통화하고, 2장 표로 각자 점수를 매긴 뒤 평균을 낸다. 한 사람의 취향으로 기준이 쏠리지 않게 하려는 것이다.

| 페르소나 | 특징 | 주로 보는 항목 |
|---|---|---|
| 어르신 | 천천히, 말 중간에 오래 쉼, 번호를 띄엄띄엄 부름 | B(말 끊기), C(번호 되묻기) |
| 콜포비아 20대 | 짧게 말하고 빨리 끝내고 싶어 함 | A(턴 수), E(선택지) |
| 화난 고객 | 사정을 길게 말한 뒤 마지막에 요구 | D(공감·결론 먼저), B |
| 숫자 실수 고객 | 주문번호를 한 자리 틀리게 부름 | C(후보로 되묻기) |
| 건강 문의 고객 | "이 약이랑 같이 먹어도 돼요?" | F(즉시 인계) |

필수 시나리오 (scenarios.md 10개에서 고름):

| # | 시나리오 | 확인 포인트 |
|---|---|---|
| U1 | 발신번호 있음 + "입금 확인해 주세요" | 묻지 않고 바로 조회(EX02) |
| U2 | 발신번호 없음 + 배송 조회 | 번호 하나만 묻기, 조회 뒤 공백 |
| U3 | 주문번호 한 자리 틀림 | 최근 주문 후보로 되묻기 |
| U4 | 출고 후 배송지 변경 | 안 된다고 분명히 말하고 인계(EX03) |
| U5 | 효과 없어서 반품 | 바로 접수 진행, 섭취 안내는 한 문장 |
| U6 | 복용약 병용 문의 | 단정 금지, 즉시 인계 |
| U7 | "상담원 바꿔 주세요" | 즉시 연결, 되묻지 않기 |
| U8 | 긴 사정 + 마지막에 질문 | 끝까지 듣고 결론부터 |
| U9 | 3턴 이상 이어지는 통화 | 채움말 반복, 재질문 없음 |

## 6. 실험안 비교에 쓰는 법

회의에서 정한 컨텍스트 실험안 세 가지를 같은 시나리오 세트로 돌리고, 5.1 정량 지표와 5.2 LLM 판정 평균, 첫 소리 p50을 한 표로 비교한다.

| 안 | 내용 |
|---|---|
| 베이스라인 | 시나리오·브랜드 정보·말투·도구를 전부 시스템 프롬프트에 넣음 |
| 도구형 | 시나리오만 넣고, 브랜드 정보는 제목만 준 뒤 필요할 때 도구로 가져옴 |
| 분류형 | 판단 모델이 문의 유형을 먼저 분류하고, 공통 + 해당 시나리오 + 관련 브랜드 정보만 넣음 |

채택 기준: **UX 점수(2장)가 같으면 첫 소리 p50이 짧은 안**을, **첫 소리 차이가 0.5초 구간 안이면 UX 점수가 높은 안**을 고른다.

## 7. 미확정

- 심사위원의 실제 체크리스트. 공지가 나오면 이 문서의 2장을 그 항목에 맞춰 다시 매핑한다.
- 심사위원이 통화할 때 발신자 정보(`caller`)가 주어지는지. U1·U3 전략이 여기에 달려 있다.
- 다중 턴 시연 방식(심사위원이 실시간으로 여러 턴을 말하는지, 정해진 대본인지).
