## 1. 결론

지금까지는 **시스템 점수(응대 50 / 함수 20 / 속도 30)를 최종 점수처럼** 최적화해 왔다. 공식 배점에서 시스템 점수는 **100점 중 20점**이다. 50점은 심사위원이 직접 써 보는 **사용자 경험**이고, 나머지 30점은 발표(20)와 기획서(10)다. 행사는 **2026-11-21(이틀 뒤)**이며, 당일 09:00에 매뉴얼·함수·데이터·측정기가 공개되고 오후에 측정한다.

목표를 다음처럼 다시 잡는다.

| 우선순위 | 목표 | 이유 |
|---|---|---|
| P0 | **당일 교체 준비**: 공식 매뉴얼·함수 정의·데이터 파일을 몇 시간 안에 반영하고, 외부 접속·동시 4개·측정기 연습까지 끝낼 수 있게 | 당일 개발 시간은 약 6시간, 측정 중 수정·재시작 금지 |
| P0 | **사용자 경험(50점)**: 중간 개입(끼어들기·정정) 대응, 같은 채움말 반복 금지, 간결함, 긴 침묵 금지 | 최대 배점, 사람이 실시간으로 평가 |
| P1 | **시스템 점수(20점)**: 특히 **함수 조회 뒤 실제 답까지 시간**(속도 점수에 평균으로 반영) | 기존 최적화가 놓친 항목 |
| P1 | **발표·기획서(30점)**: 설계 근거, Human Handoff 기준, 속도·품질 trade-off, 측정 결과 | 지금까지의 실측 기록이 그대로 근거가 된다 |

## 2. 공식 내용 vs 우리 가정

| 항목 | 우리 가정 | 공식 내용 | 영향 |
|---|---|---|---|
| 총점 구성 | 응대 50 / 함수 20 / 속도 30 | **사용자 경험 50(정성) + 응답 품질·기능 20(시스템 점수 ÷ 5) + 발표 20 + 기획서 10** | 시스템 점수 비중 축소, UX·발표 비중 확대 |
| 시스템 점수 | 같음 | 응대 50% + 함수 20% + 속도 30%. 응대는 문항별 맞음 1.0 / 괜찮음 0.7 / 틀림 0 | 채점기 구조 동일 |
| 속도 | 말 끝 → 첫 소리 | **함수 문항은 첫 소리 점수와 "조회 결과 뒤 실제 답까지 시간" 점수의 평균**. 채움말도 첫 소리로 인정 | `after_tool_sound` 최적화 필요(지금 툴 결과 뒤 LLM 재호출 1~3초) |
| 채움말 | 모든 턴에 캐시 첫 마디("네, 고객님.") | **"모든 응답을 채움말로 시작"은 시스템 점수만 높이는 설계로 보아 좋은 평가를 받지 못함**, UX 감점 사례 "모든 답변에 같은 채움말 반복" | 첫 마디 전략 재설계 필요 |
| 중간 개입 | 측정기는 끼어들지 않으니 후순위 | **UX 심사 요소: "고객의 중간 개입이나 추가 질문에 대응"**, 감점: "중간 개입(정정, 추가 질문) 무시" | 바지인(상담원 발화 중 고객 발화 → 즉시 중단·재응답) 구현 필요 |
| 도메인 | 일반 쇼핑몰(의류·전자 등) | **건강기능식품 쇼핑몰**. 업무 7종: 배송, 주문 취소, 반품·환불, 교환, **결제**(수단·입금), **상품**(정보·가격·이용 방법), 상담원 연결 | 연습 데이터·시나리오를 건강기능식품으로 바꿔야 의미 있는 리허설 |
| 상담원 인계 | 욕설·강한 불만·반복 실패·직접 요청 | 예시: **제품 섭취 후 몸이 불편하다는 문의 → 상담원 연결**. 기준은 팀이 정의하고 기획서·발표에서 설명 | 건강 이상·의료 질문 인계 규칙 추가 |
| 숫자 | 주문번호 10자리 가정 | 예시 "주문번호 1234", "공일공/영일영" 대응 | 자릿수 규칙(10자리 검사·교정)을 공식 데이터 기준으로 바꿔야 함 — 지금 규칙은 위험 |
| 업무 원칙 | 매뉴얼 기반 | "확인되지 않은 정보 안내 금지", "필요한 정보를 받기 전에 업무 실행 금지", 매뉴얼에 없는 정책 금지 | 프롬프트 규칙과 일치 |
| 측정 | 로컬 측정기 | 운영진 노트북 측정기가 **비공개 시험 문항 4개 동시**, 팀 서버 주소(노트북 IP 또는 **터널 주소**)로 접속, **측정 중 수정·재시작 금지** | 외부 접속·안정성·동시성 사전 시험 |
| 함수 호출 | Mock 서버 직접 | 측정기의 **함수 중계(`tools_url`)**를 거침. 주소 고정 금지, `X-Session-Id` 필수 | 이미 `tools_url` 사용 ✓ |
| Mock 데이터 | 코드에 고정 경로 | **실행 시 파일로 데이터를 받음**, 측정 직전 시험용 데이터 파일 전달 → 그 파일로 재기동 | Mock 서버에 데이터 파일 인자 필요 |
| 채점기 | Gemini judge(우리) | 공식 채점기는 **받아쓰기와 채점에 OpenAI API** 사용 → 연습 측정에 OpenAI 키 필요 | 당일 OpenAI 키 준비(AG-U01). 상담원 음성은 OpenAI STT로 다시 받아써서 채점될 가능성 → TTS 명료성 중요 |
| 모델 제한 | 미확인 | **AI 모델·STT·TTS 종류 제한 없음**, API 키·이용료는 팀 부담 | Gemini·edge 사용 가능(edge-tts는 비공식 서비스라 당일 장애 시 대체 필요) |
| 실격 | — | 측정 중 사람이 대신 답, 시험 음성 저장·유출, 측정기 우회 | **시험 음성 저장 금지** → 턴 로그·오디오 저장 기능을 측정 때 꺼야 함 |
| 일정 | 2~3주 가정 | **11/21 하루**: 09:00 자료 공개, 15:00 중간 리뷰, 16:00–18:30 마무리·기획서 제출, 오후 측정, 19:00 발표(7분+질의 3분) | 당일 작업 순서표 필요 |

## 3. 잘 맞는 부분 (유지)

- WebSocket 측정기 프로토콜, `tools_url`·`X-Session-Id`, 동시 세션 처리, 말 끝 전 발화 0점 회피 설계.
- 응대 매뉴얼 기반 LLM + 함수 호출 + 사실 확인(조회 결과 반영) 구조.
- "공일공/영일영" 숫자 정규화(AG-T08), 필요한 정보 전 실행 금지 규칙(AG-T10a).
- 모든 판단을 실측으로 남긴 기록(`docs/decisions/`) — 발표 "Evaluation Result", "Failure / Improvement"에 바로 쓸 수 있다.
