## 공식 규격 (AG-T36, 기본)

- `tools.json`: 공식 `directon-2026-voice-cs/data/brand/tools.json` 사본(함수 8개). 개인정보 없는 계약이라 저장소에 둔다(AD14).
- 데이터는 저장소에 넣지 않는다. 연습 `directon-2026-voice-cs/data/mock_db.json`, 최종 측정은 운영진의 `mock_db_test.json`.
  `{함수명: [{"arguments", "result"}]}` 모양, 결과 키는 한글(`주문번호`, `배송상태` …).
- 실행: `uv run python -m mock_api.server --port 8100 [--db <mock_db.json>]`(기본 `DIRECTON_MOCK_DB` → 공식 폴더), 제출용 `bash start_mock.sh <데이터>`.
  테스트에서는 `mock_api.server.load_store(path)` / `create_server(port=0, store=...)`.
- 응답 규칙은 `mock_api/server.py` 머리말. 같은 인자로 결과가 둘 기록된 경우(연습 3건)는 첫 기록을 돌려준다.

## 옛 체계 (다이렉트몰 14개 함수, 정리 예정)

아래는 공식 명세 전 가정한 가상 쇼핑몰이다. `mock_api/legacy_shop.py` + `legacy_tools.json` + `mock_data.json`.
옛 172문항 testset·오프라인 LLM 평가·데모가 새 체계로 옮겨지면 지운다(AG-T38·T40, AD15).

- `legacy_tools.json`(옛 `tools.json`): 함수 14개 정의(이름·한국어 설명·JSON Schema). `GET /tools`가 `[{"type":"function","function":...}]`로 감싸 준다.

## matched 판정 규칙

1. **인자 검사(먼저).** 아래 중 하나면 `{"status":"invalid_arguments"}`, `matched=false`.
   - 스키마에 없는 인자가 있다(예: `extra`).
   - 필수 인자가 없다.
   - 값이 문자열이 아니다(예: `"order_id": 2611150231` 숫자형). 필수 인자가 빈 문자열이다.
2. **키 인자 정확 일치.** 키 인자는 `phone_number`, `order_id`, `product_name`, `option`. 데이터의 값과 **문자 그대로** 같아야 한다(정규화 없음).
   - `010-1234-5678`(하이픈), `2611 150231`(공백), `이어폰`(상품명 일부)은 모두 불일치 → `{"status":"not_found"}`, `matched=false`.
   - 인자 정규화는 상담원 쪽(AG-T08) 책임이다.
3. **자유 텍스트 인자는 판정에서 제외.** `reason`, `new_address`, `preferred_time`은 어떤 값이든 matched와 응답 내용에 영향을 주지 않는다(필수인 `new_address`, `transfer_to_agent.reason`은 비어 있지만 않으면 된다). 기록(`/calls`의 `arguments`)에는 그대로 남는다. 시나리오의 `expected_tools`에 자유 텍스트 인자를 적더라도 채점기는 키 인자만 비교하는 것을 권장한다.
4. **키 인자가 데이터에 있으면 matched=true.** 업무상 거절이어도 matched다. 예: 배송중 주문의 `cancel_order` → `status: not_allowed`, `matched=true`. 환불 내역이 없는 주문의 `get_refund_status` → `status: no_refund`, `matched=true`.
5. `check_stock`의 `option`은 선택이다. 빼면 전체 옵션 재고를 주고 matched=true. 넣으면 그 상품의 옵션명과 정확히 같아야 한다(다르면 not_found, matched=false, 응답에 `available_options`).
6. `transfer_to_agent`는 키 인자가 없어 `reason`만 있으면 항상 matched=true.
7. `request_callback`은 등록 회원 번호만 matched(비회원 번호 → not_found).
8. 서버는 상태를 바꾸지 않는다. `cancel_order`를 불러도 주문 상태는 그대로이고, 같은 입력은 항상 같은 출력을 준다.
9. HTTP 수준: 모르는 함수 → 404, JSON이 아니거나 객체가 아닌 본문 → 400. 둘 다 `/calls`에 기록하지 않는다.

## 응답 status 값

| status | 뜻 | matched |
|---|---|---|
| ok | 정상 처리 | true |
| not_allowed | 주문은 있지만 상태 때문에 처리 불가(`message`에 대안 안내, `data.status`에 현재 상태) | true |
| no_refund | 주문은 있지만 환불 내역 없음 | true |
| not_found | 키 인자가 데이터에 없음 | false |
| invalid_arguments | 인자 형식 오류(1번 규칙) | false |
